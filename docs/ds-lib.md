# 结构库 / 算法库：分类与目录

> **结论先行**：结构库按 **形状 × 生命周期** 两轴组织；判据不是"教科书上有没有"，
> 而是**有没有真实调用方**。本轮只补三件（`csr` / `pqueue` / `vec`），其余明确不做并写明触发条件。
> 算法库只收**连续内存上的通用变换**。

## 0. 什么进库：三类判据

| 类 | 判据：拿掉它，结构还自洽吗 | 例子 |
|---|---|---|
| **结构** | 拿掉就不成立（它就是形状） | arena / table / ring / str / sb / bitmap / buf / blob / namemap |
| **算法** | 拿掉仍自洽，只是缺一种变换 | sort / lower_bound / topk / hash / toposort / reach |
| **契约** | 拿掉结构没事，**用法**失去保证 | handle 世代+class、phase、HARD/SOFT、`cxf_result`、allocator |

三条硬边界（违反即设计漂移）：

1. **algo 不收某结构的成员函数。** swap-remove 依赖 sparse/dense 的对应关系 ⇒ 属 table；
   二分查名字依赖条目布局 ⇒ 属 namemap。搬进 algo 只是换文件夹 + 多一层间接。
2. **结构不持有 world、不做分配策略。** 视图型（str / sb / bitmap / csr）由调用方给内存；
   拥有型（buf / blob）显式持 allocator；没有任何结构自带全局态。
3. **没有调用方不进库。** 只写不用的结构会以"看起来已解决"的形态腐烂
   （DialogMesh 的 `PosteriorCorrector` 就是先例）。

## 1. 两轴分类

**轴一：形状**（按怎么找元素）· **轴二：生命周期**（按谁负责释放）

| 形状 | 视图（不拥有，调用方给内存） | 拥有（显式 allocator） | 池（handle 交接） |
|---|---|---|---|
| **栈式内存** | —— | `arena`（帧栈） | —— |
| **线性字节** | `str` / `sb` | `buf` | `blob` |
| **定宽元素** | —— | `vec` | —— |
| **按标识随机访问** | —— | —— | `table`（稀疏集）/ `soa` |
| **按键关联** | —— | `namemap`（arena，只读） | —— |
| **按优先级** | `pqueue` | —— | —— |
| **按位** | `bitmap` | —— | —— |
| **图** | `csr` | —— | —— |

读法：**同一形状换了生命周期就是另一个结构**，不是一个结构的"可选模式"。
`str` 与 `buf` 都是线性字节，但前者不拥有、后者拥有 —— 混用就会出现
"这个指针谁 free"的问题，而那正是 GC 存在的前提。

### 明确不做（写明触发条件，避免"以后再说"变成"永远在加"）

| 不做 | 理由 | 什么情况下才做 |
|---|---|---|
| 通用哈希表 | 注册表只读 ⇒ `namemap` 已够；运行期键值查找**当前零调用方** | 出现"每 tick 按字符串查表"的真实路径 |
| 单/双链表 | `table` 的 free 链已覆盖；链表 = 指针 chase，与可预测地址相悖 | 需要 O(1) 任意位置摘除且不能搬行 |
| 平衡树 | 规模 ≤ 数百，排序数组的 O(n) 插入无所谓 | 单次装配插入超过 ~10⁴ |
| trie | 前缀枚举用 `lower_bound` + 顺序扫已够 | 需要按公共前缀压缩存储 |
| deque | `ring` 覆盖 | 需要两端插入且随机访问 |
| 拥有型 string | `blob` + `str` 组合 | 不要做（会让"谁复制"重新变成隐式约定） |
| 动态图（邻接表 + 增删边） | 装配期定型，运行期只读 | 出现运行期改图的需求（目前没有） |

## 3. 逐件规格（落地的写"已落地"，未落的写判据）

### `csr`（P0，已落地）

- **形状**：`off[n+1]` + `adj[m]`。节点 i 的出边是 `adj[off[i] .. off[i+1])`。
- **不变量**：C1 `off[0] == 0`、`off[n] == m`、`off` 单调不减；C2 `adj` 全部 `< n`；
  C3 同一节点的出边按输入顺序排列（确定性）。
- **复杂度**：建 O(n+m)，**零临时数组**（两遍计数 + 逆序填 + 左移一位）；
  查询 O(1) 取区间；`toposort` / `reach` 均在上完成，不需要额外索引。
- **消掉的错误**：邻接表的 `next` 指针 —— 遍历不再依赖"下一条在哪"这个运行时数据，
  而是区间边界；链编址错误导致的自环也不可能再发生（区间算错只会越界，check 抓得住）。
- **调用方**：`world.c` 的依赖图（Kahn 已下沉，见 §4）、`catalog_rebuild` 的不变式 6/7/8、
  L1 的增边查环（`v` 能否到达 `u` 用 `reach` 或反向 `csr`）。
- **下沉记录（`world.c`）**：局部 Kahn 删除，改成"`build_graph` 产出边表 → `cxf_csr_from_edges`
  建一次图 → `cxf_algo_toposort`"。三处顺带的变化：
  1. 拓扑排序从 O(n·m)（每个节点扫一遍全部边）变成 O(n+m)；
  2. `refcount` 不再逐边 `++`，直接取**出度** `cxf_csr_deg` —— "有几个模块依赖我"就是"有几条边从我出发"；
  3. 未加载模块在图里是孤立点（建图只连接两端都 loaded 的模块），所以排序后按 `loaded`
     过滤即可，不影响环检测（`cnt == n` 的判据与"已加载全定序"等价）。
  另外 `cxf_csr_check` 在建图后断言一次：装配期门口查得动的东西，不要留到运行期。
  **这次下沉当场又撞了一次同一类错误**：csr 的字节数原本在释放时用 `cxf_csr_bytes(n, edges.len)`
  重算，而前一行 `cxf_vec_free(&edges)` 已经把 `len` 清零 ⇒ 少释放 m*4 字节。
  `test_world.test_release_accounting` 立刻抓住。**结论：释放用的 size 必须是申请时存下的值，
  不能事后从可变状态重算** —— 这与"申请和释放用同一个算式"是同一件事的更强表述。

### `pqueue`（P0，已落地）

- **形状**：`(uint32 key, uint32 id)` 数组 + 规模，视图（调用方给数组，满返回 false）。
- **不变式**：P1 `0 <= n <= cap`；P2 父不大于子；**P3 `less` 是全序 —— key 小者优先，
  key 相等时比 id**。P3 不是锦上添花：缺了它，相等 key 的弹出顺序取决于内部移动历史，
  同一组任务在不同插入序下给出不同调度序，日志与断言都不可复现。
- **操作**：`push` / `pop` / `peek` / `make`（自底向上建堆，O(n)）/ `update_at`（decrease-key 原语）/ `find_pos` / `clear`。
- **消掉的错误**：每 tick 全排序 O(n log n)；有序数组插入的 O(n) 搬移；**相等 key 的调度序不可复现**。
- **边界（`make bench` 可复现）**：本结构只对**增量**名副其实 ——
  反复取最小不重排、只取前 k 个不必排出全部。**"全量建立 + 全量排空"不该用堆**：
  排空是沿树下沉、每层一次 cache miss，而全排序是连续扫描，"make + 全弹"明显慢于
  "排序 + 扫"。同一份基准上"建堆 make"与"建堆 n×push"的比约 1 : 2 —— 那才是
  `make` 存在的理由（O(n) 对 O(n log n)），而不是"让堆打败排序"。
- **落地时修正的两条错判**：
  1. 原规格写"`sift_key`（id → 位置需外部 map，先不做）"，理由是"调用方维护 id → pos"。
     这条**做不到**：pos 在每次 push / pop 后会变，外部观察不到，而要让库回调它就成了
     回调（宪法第 4 条禁止）。实际提供 `find_pos`（O(n) 线性扫）+ `update_at`。
     要严格 O(log n) 得让结构自持一列 pos 并在每次 swap 时同步两个数组 ——
     等调度器真把堆当 Dijkstra fringe 时再加。
     **教训：凡是"调用方维护一份镜像"的设计，先问那份镜像能不能被观察地更新。**
  2. 只做 `push` 会漏掉 O(n) 建堆这条路径，导致"堆比排序慢"的假象被归因到堆本身。
     补 `make` 之后，慢的部分被定位在**排空**（结构固有的随机访问），而不是建堆。
- **调用方**：调度器（超时与优先级）、L3 的 top-k 增量维护。

### `vec`（P1，已落地）

- **形状**：`{cxf_alloc *alloc; void *p; uint32 len, cap, elem}`，`len/cap` 以**元素**计。
- **边界**：不做 `void*` 泛型模板，元素宽度作为参数；**增长策略是唯一实现**
  （`cxf_vec_grow`），`buf` 是它 `elem == 1` 的退化情形，五处注册期数组都直接调它。
- **为什么"容量必须和指针放在一起"**：落地时在 `world.c` 抓到两个真实缺陷 ——
  `edges` 用 `ecap` 申请、用 `ecount` 释放；`order` 用 `(n+1)*4` 申请、用
  `module_count*4` 释放。堆分配器的 `heap_free` **忽略 size**，所以两者都不崩、
  不漏内存，只让 `bytes_live` 单调漂移（实测 `world_release` 后残留 124 字节）。
  换成任何在意 size 的 allocator（池 / 共享段）就是堆损坏。
  把 p/cap 绑成对象后，这类错误**没有表达方式** —— 不是"记得别写错"，是写不出来。
- **验收**：`test_vec`（增长后前缀逐项不变、`push_slot` 未初始化契约、宽元素步长、
  释放后 `bytes_live` 归零、重复 free 幂等）；`stress_vec`（影子数组对拍 20000 步，
  抽样回读 + 原地改写可见 + 收尾全量比对）；`test_world.test_release_accounting`
  （`world` 反复 `start` 后释放，记账必须回到原点 —— 这是上面两个 bug 的永久回归）。
- **消掉的错误**：六份手写倍增各自的边界判断；**申请算式与释放算式不一致**。
- **不做**：按下标插入/删除（memmove 是另一个语义，等有调用方）；多列 SoA
  （`table` 的列容量一次长一组列，不是单个数组 —— 形状不同，不硬套）。
- **未做的迁移（机械，非缺陷）**：`world` 的 `modules` / `services` / `types`
  三对 `(T *p, count, cap)` 仍散装，但它们释放时用的都是 cap、当前正确。
  迁到 `cxf_vec` 是纯机械替换，等下一次改 world 时顺手做。


## 5. 命名与验收

- 命名：`cxf_<结构>_<动词>`；视图型用 `_view` 或"函数只读"，拥有型在签名里显式带 allocator。
- 每件必须齐四段：头文件写**不变式 / 复杂度 / 代价 / 不适用**；`.c` 只写"为什么这样做"。
- 验收：单测 + **压力测试**（随机序列对拍，确定性种子）+ `check()` + 三构建
  （debug / NDEBUG / ASan+UBSan）。缺一项不算落地。
