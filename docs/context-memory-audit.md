# 上下文单份存储与长上下文内存审计

> 统一数据展示见 [测试成果汇总](benchmarks/README.zh-CN.md#e0709--上下文存储与临时内存)（E07–09）：成功／FULL 拒绝、临时堆／token 存储／RSS／KV 分开列出。

2026-10-30，实施前记录。目标：区分长期上下文、瞬时副本和 KV；不再以任务能力评分。
状态更新：审计、生命周期调整及长上下文验收已完成。结论是**核心 token／显式分支共享有效，
但尚不能称全链路最少副本**。
最新一轮已接入直接 Jinja 值、只读结果收集与有界分词首次尝试；
当前实现与数据见[本轮结果](#直接-jinja-值的实现与实测)。前面的各轮数据保留为阶段历史，不能跨轮混作基线。

源码初步审计：应用 transcript blob 为一份，原生后端 token 块为一份，分支借用块。
原文事件、token 和 KV 是不同表示，不能把“只有一个 canonical token owner”说成
整个系统只存一份上下文信息。libllama 直接库路径不启动 llama-server，后者的 slot
prompt/token 历史不在此路径内；KV 本身仍独立存在并随长度增长。

初次审计时临时重叠包含：请求 JSON 字符串、JSON DOM、解析出的 messages、规范化消息 JSON、
Jinja 工作内存、完整渲染文本和后缀 token scratch。当时计划提前释放用完的中间表示；
不删除事件，不截断上下文，不更改模板内容，不新增持久历史。

测量契约：

- 增加仅诊断构建启用的阶段探针，记录已知文本表示的逻辑字节数；不是实际分配字节。
- macOS malloc 全 zone 在用字节与定时采样峰值作为辅助；不是显存，也不保证捕获亚毫秒尖峰。
  RSS 单列，受引擎、共享映射和分配器保留影响，不用 RSS 不降来断言文本没释放。
- 原生命周期／提前释放两档同进程对照；正常计时与内存探针分开，避免把探针开销当成性能。
- 真实 KV 在本机可承受的上下文范围测；更长文本超过 KV 容量时，只测前端拒绝前的内存，
  明确标记为失败路径，不当作长 KV 兼容通过。
- 多分支统计 stored/logical token、池容量和新 decode 数量，验证共享与关闭回收；
  不把序列删除说成物理 KV buffer 归还。
- 固定模板／真实 libllama 的 token 和动作对照继续通过才接受生命周期调整。

## 长期到底存了什么

| 层 | 当前归属 | 是否另一份完整上下文 |
|---|---|---|
| 原始 transcript／工具事件 | 应用 blob | 一份原文事件表示；同一父 blob 继续追加，不逐轮另存全文 |
| canonical token | 原生后端的共享块池 | 一份 token 表示；独立 session 不自动去重，显式 fork 才共享 |
| KV／位置与序列归属 | libllama context | 计算状态，仍需独立内存；不是因为 token 单份就消失 |
| decode batch | libllama／后端 | 有界 batch scratch，不保留完整历史 |
| 模板 AST／解析器 | 原生桥 | 固定格式元数据，不保存消息历史 |
| `/context` 诊断快照 | agentctl | 额外的有界副本：prompt 64 KiB＋action 16 KiB |
| 显式 `--trace` | 用户指定文件 | 每轮可重复写入全文，磁盘量会累积；默认不开启 |

应用 blob 在容量翻倍时会短暂并存旧／新缓冲并搬运全文；这不是每轮复制，但还不是
分块事件存储。工具回路当前 `AGENT_ARGS_MAX=64 KiB`、初始输入上限 2048 B，
原生桥的输入／渲染上限为 1 MiB。本报告的更长输入通过后端 API 测试，不能等同于
现有 CLI 已支持任意长任务；没有悄悄放宽这些上限。

libllama 直接 C API 中，tokenize 的内部临时 vector／字符串和 decode 的批次输入仍会
复制数据。固定 b10938 的 `src/llama-vocab.cpp` 中，容量查询也先完成分词再返回所需长度。
因此先查询、再提供缓冲区的辅助分词接口会做两次分词；超出 KV 容量的拒绝也可能已经
支付了较大的分词临时开销。当前没有改写该上游接口；最新桥接路径先提供有界缓冲，
只在容量不足时重试，见本轮结果。

## 已实施的修改

把不再使用的请求字符串和 JSON DOM 提前释放；快路径构造完规范化消息后释放原 messages；
渲染完释放剩余 messages。不改变原文、模板、token 或 KV 的语义。

普通构建总是采用提前释放；仅 `CXF_CONTEXT_AUDIT` 诊断构建可切回旧生命周期作对照。
探针和回调不进入正常构建。该变化不声称消除所有临时副本：请求→DOM→messages
转换时仍有重叠，Jinja 与 tokenizer 也有自身工作内存。

## 实测：长期 token 与分支共享

环境：Apple M5、16 GiB 统一内存、Qwen3-0.6B-Q8_0、固定 b10938，16K KV 池，
FP16 KV，batch=512，4 CPU 线程，最多 9 session。每条测试顺序执行，没有并发加载其他测试模型。

一条正常长输入的逻辑 token 数为 **14504**：

- token ID 的逻辑下限 58016 B（56.7 KiB）。物理块保留 14511 token，额外 7 个来自
  保守检查点留下的有界块尾；不是另一份完整前缀。
- token payload 池容量 59392 B，cxf 分配器负责的块／索引／session 等合计 **65260 B**
  （63.7 KiB）。这不包含应用原文、C++ 模板元数据、libllama 分配或 KV。
- 同一上下文重复同步后没有按轮数保留新的完整 token 历史；池容量／索引保持稳定。

显式 fork 的真实 KV 测试：

| 阶段 | 逻辑 token 合计 | 实际存活 token | token 池容量 | 新 decode |
|---|---:|---:|---:|---:|
| 6000-token 前缀，8 个共享视图 | 48000 | 6000 | 24576 B | fork 不重算前缀 |
| 各自追加 32 token | 48256 | 6256 | 31744 B | 共 256 token |

fork 前后 cxf 在用字节均为 30444 B，没有再分配前缀 payload；继承 KV 的序列归属累计
42000 token。关闭这些视图后 payload 清零；关闭引擎后 cxf 分配器存活字节为零。
48K 逻辑前缀在 16K 物理 KV 池内继续 decode，证明前缀 KV 没有按八个分支各存一遍。
此结果来自显式 fork API 验收，不代表当前单 session 的 agentctl 已自动把所有子任务接到它。

## 实测：临时副本与峰值

固定输入每档三次，交替顺序。已预热格式元数据与当前上下文，只比较暖态同步；
以下为“调用期间采样到的 malloc 在用字节峰值−调用前在用字节”的中位数，**不是总进程内存**。

| 输入形状 | 结果 | 原生命周期 | 提前释放 |
|---|---|---:|---:|
| 单文本，14504 个逻辑 token | 真实 KV 成功 | 591.9 KiB | 324.9 KiB |
| 128 条工具记录，5543 个逻辑 token | 真实 KV 成功 | 1786.2 KiB | 1595.0 KiB |
| 512 条工具记录，输入 53.8 KB | 超 16K KV 容量，FULL | 6990.2 KiB | 6280.9 KiB |
| 约 64K 个 `alpha`，输入 393.2 KB | 超 16K KV 容量，FULL | 10355.8 KiB | 9154.0 KiB |

正常长输入的中位峰值约下降 45%。相同输入在 rendered 阶段的确定性逻辑载荷计数，
从 345236 B 的请求／DOM 消息／messages／渲染文本并存，降到仅 86757 B 的渲染文本；
调用者原始输入仍在外部，不包含在这个阶段合计中。提交时桥持有的两个 token vector
容量合计为 56 B，不包含 libllama 自己的临时容器；
在该重复同步 fixture 中不随前缀长度增长；首次／替换整个前缀时不成立。

峰值为 200 微秒定时采样与阶段观察点合并的结果，会漏掉短尖峰，不是逐次 malloc 精确追踪。
14504-token 档的原峰值范围为 590.4–971.2 KiB，提前释放为 316.2–801.4 KiB，有重叠。
小输入也不保证下降：约 1.2K token 的样本中，采样中位数从 49.7→74.6 KiB。
不要把一次生命周期调整宣传为所有长度均固定降低某个百分比。

多条小消息的元数据／Jinja 开销仍明显。阶段定位显示工具记录组峰值主要在 normalized
观察点之后、rendered 之前；超长单文本拒绝组则主要在 rendered 之后的分词容量查询区间。
这是分阶段定位，未替代完整分配调用栈追踪。

调用返回后，大部分重复样本的 malloc 在用增量为零；首次样本有少量正负缓存波动。
RSS 在正常长输入两档均约 2474 MiB，未随这几十至几百 KiB 的临时释放相应下降。
分配器可保留空闲页，而且本轮实测 KV buffer 自身就有 **1792 MiB**。对应本模型每个
配置 KV token 约 112 KiB；只是本模型／本配置，不能外推到其他模型或 KV 类型。

没有内存探针／采样线程的独立计时中，长输入暖态同步中位数 36.742→37.203 ms；
128 条工具记录 37.348→36.700 ms。本次没有可靠提速结论，主要改进是缩短重叠存活期。
这些计时不含首次长 prefill，也不包含完整生成。

## 直接 Jinja 值的实现与实测

本轮未修改 llama.cpp 源码。沿用固定 b10938 的 common/Jinja C++ 类型与 runtime，
这些不是稳定的 libllama C ABI；升级依赖仍需重新验收。

- 已验收模板的缓存命中路径从借用事件直接构造 Jinja 消息值，不再经过完整规范化 JSON 树
  及其到 runtime 值的复制。字符串值保留 `is_input=true`，对象键沿用上游的非输入标记。
  工具元数据仍经上游 JSON 转换；冷准备／未知模板仍使用完整上游入口。
- 保留上游 AST 执行。对其结果树先只读计长，检查 1 MiB 上限，再一次预留连续字符串并顺序写入；
  跳过 `gather_string_parts` 的结果 parts 副本及随后的重复拼接。数字、布尔值、忽略节点及 NUL
  的输出规则与上游一致；不修改来源标记，也不持久保存树或渲染文本。
- 分词首次缓冲为 `min(context, max(32, bytes/4+32))` 个 token，空文本为零；
  容量不足时释放无效输出并按返回长度重试一次。超过 context 直接报 FULL，绝不截断。
  这是容量猜测，不是假设英文／中文有固定 token 比率；中文 fixture 已覆盖真实重试。
- 逻辑 token 数、实际 tokenizer 调用次数、重试次数与桥接 scratch 容量分别计数。
  上游 tokenizer 仍会建立内部字符串／vector；新路径没有做到零复制。

对照基线是上一轮的**直接消息＋规范化 JSON＋先查询再分词**，不是更早的完整 HTTP 请求路径。
固定输入、同进程暖态交替顺序、每档三次；内存采样与计时分开。环境和 16K KV 池沿用前文。
这次同时启用直接输入值、结果收集、分词缓冲三项改动，不能把整体收益单独归因于其中一项。

采样临时堆峰值中位数及三样本范围：

| 场景 | 结果 | 上一版规范化 JSON | 直接 Jinja 值 |
|---|---|---:|---:|
| 14504 个逻辑 token，单段文本 | 真实 KV 成功 | 511.7 KiB（410.8–608.9） | 141.3 KiB（125.0–214.4） |
| 128 条工具记录，5543 个逻辑 token | 真实 KV 成功 | 1490.9 KiB（1487.7–1493.7） | 1192.2 KiB（1184.7–1192.8） |
| 512 条工具记录 | FULL 拒绝路径 | 5939.8 KiB（5859.3–6010.6） | 4671.8 KiB（4666.8–4766.6） |

成功长文本档约下降 72%，128 条工具记录档约下降 20%。不能外推为所有长度都会改善：
约 7.3K token 档从 67.1→84.0 KiB；64K 单文本拒绝档反而多 64 KiB，来自新的有界输出缓冲，
而此时主要开销仍在上游完整分词。内存采样会遗漏短尖峰，范围和原始样本均保留。

没有稳定的整体提速结论。无采样线程的暖态总同步中位数：长单文本 34.581→35.085 ms，
128 条记录 35.610→37.104 ms；长单文本渲染计时 0.438→0.425 ms，分词 0.032→0.026 ms。
重复同一上下文的 API 调用从 4→2（空 delta＋generation header，各调用一次），
不代表 token 工作量或端到端耗时减半。超过 context 的拒绝路径两档均调用一次后停止。
首次长 prefill 与完整生成不在这些暖态同步计时之内。

长文本重复同步提交时，两份桥接 token vector 的容量合计从 56→196 B；这是为减少查询重试
付出的额外 scratch，不应隐藏。重建整个前缀时首次缓冲最多 context 个 token，失败时也可能存在；
遇到重试先释放旧 scratch，delta／header 本身仍有短暂重叠。
原生分配器的长期数据未增加：14504 个逻辑 token 对应物理块 14511 token、
payload 池 59392 B、cxf 总在用 65260 B。RSS 约 2480 MiB，未随临时峰值下降；
1792 MiB 的预分配 KV buffer 未变。8×6000 前缀共享、各追加 32 仅新增 decode 256 的复测继续通过。

验收包括 256 组字节语料的消息字段与来源标记、混合结果树与上游收集器逐字节对照、
UTF-8 拒绝、中文分词重试、工具动作、14357-token 独立全文分词／KV 后缀复用，
以及 ASan／UBSan、原生 CLI 和默认 `make test`。预编译上游动态库本身未加 sanitizer。
这些仍是基础设施兼容验收，不是 0.6B 自主修复能力评分。
