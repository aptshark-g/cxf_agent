# 管道计划（Pipe Plan）：动作之间的数据流与断点续跑（评审提案 v0.1）

> 状态：提案，未落码。前置已落地：轮内 fan-out（`agent.md §4.17.9`）、
> `agent.action` 首尾相接线格式（`agent_action.h` v1.13）、WorkItem fan-in /
> blob 交接 / "失败不悬空"断言（`tests/test_agent.c`）。
> 产生缘由：与 pi codemode / codex / Hermes 的对标（2026-10-23），
> 结论记录在本文件 §0，逐档定位见 §6。

## 0. 这格为什么存在：codemode 的对照暴露了一个空档

对标 pi codemode（模型写 JS、沙箱执行、中间结果不进上下文）时，它的代价
被完整看到了：**失败是整块的**。一个幻觉路径让整段脚本作废，前缀工作全部
丢失；恢复方式是降级到逐步式从头再来。

而我们的轮内 fan-out（§4.17.9）只覆盖了一种形状：**N 条互相独立的动作**，
结果各自回模型。动作之间没有数据流——"步 k 的 result 作为步 k+1 的 args"
这种最常见的批处理形状，目前只能拆成 N 轮模型调用，每轮付一次完整的前缀
与一次调度往返。

两个参照物之间有一个空档，这就是本提案的位置：

| | 控制流在哪 | 失败时 | 解码器 | 小模型适配 |
|---|---|---|---|---|
| 轮内 fan-out（已有） | 无（并行） | 整批失败不部分应用 | 1 个 | 好 |
| **管道计划（本提案）** | 运行时按序执行 | **断点续跑**，前缀结果复用 | **1 个** | 好 |
| 逐步 CALL（默认档） | 模型跨轮推理 | 每步地面真值 | 1 个 | 最好 |
| code.run 脚本（可选） | 模型写的 JS | 整块作废，降级逐步 | JS 解释器 | 差（偏云端强模型） |

一句话定位：**管道计划 = 把 codemode 的"一轮生成、运行时执行"拿过来，
但用数据（我们训练过的 `CALL|cap\nargs` 形状）代替代码（JS），
于是失败粒度从"整块"细化到"一步"，且不引入任何新解码器、不引入脚本沙箱。**

它与 codemode 的本质区别是哲学性的：codemode 给模型一个**语言**，
管道计划给模型一个**我们语言的批处理模式**。我们的承重墙（单解码器、
模型输出只被解析绝不被执行、字节确定性）一条不动。

## 1. 合法判据：步间衔接必须是数据性的（HARD，不是配置项）

管道有一个结构性前提，必须先写成判据再谈机制：

> **步 k 的衔接是数据性的 ⟺ 步 k+1 的 args 可以由运行时从步 k 的 result
> 机械得出，无需理解其语义。**

- 满足 ⇒ 可以进管道：运行时拼接，零模型调用，断点可续。
- 不满足 ⇒ 必须断管，模型在环："如果 grep 结果里提到了 X 就做 Y"——
  判断所需的信息只在模型的世界里，硬塞进管道等于让运行时替模型做语义判断，
  而它没有那个能力。这不是缺陷，是信息位置问题（与
  `docs/agent.md §2.1` 三层检查同一判据：判定信息住在哪）。

推论：**管道的断点是设计出来的，不是优化出来的**——每个断点处自然产生
一次模型调用，这个轮次成本是买"语义衔接"的，不该被管道省掉。

## 2. 数据结构（先定结构，行为是机械的）

### 2.1 计划 = 首尾相接的动作序列（格式零改动）

复用现有线格式（`agent_action.h`）：模型一次产出 N 条 `CALL` 动作首尾相接，
**不加新 kind、不加分隔符**——v1.13 的"自定界头"就是为此留的。
"这是一串管道而非一批并行"由**消费方式**表达，不由格式表达：

- fan-out 消费：全部派生、各自回模型（现状）；
- 管道消费：按序派生、result 依次交接（本提案）。

判别位置在**解析层一处**（`inject_actions` 的调度分支），下游零改动——
与"清单走协议、动作走文本"（§4.16）同一个手法：协议通道只换表达方式，
不长新解码器。

### 2.2 数据流边：v1 只做"裸串联"（out → 下一步 args 全量）

两种衔接里 v1 只做简单的：

| 衔接 | 语义 | v1 |
|---|---|---|
| 裸串联 | `args[k+1] = result[k]` 全量 | **做** |
| 端口映射 | `args[k+1] = result[k]` 的某个命名部分 | 不做（没有调用方） |

**为什么裸串联可以不加任何格式**：衔接合法性用**现有的 TTN 端口**判——
`cat_out[k]` 产出的接口类型必须与 `cat_in[k+1]` 声明的接口类型一致。
这是注册期就建好的结构（`agent.md §10.6`），不是运行时解析。
端口不匹配 ⇒ 解析期拒绝整条计划（响亮失败），**不猜、不截断、不降级成
并行**——与 fan-out"整批失败不部分应用"（§4.17.9）同一纪律：
部分执行会让缺失步骤的输出从上下文里消失，模型无从得知。

由此得到一条类型级不变式：

> **P1 管道内相邻两步的接口必须可接**（`cat_out[k] == cat_in[k+1]`），
> 判别在解析层，失败拒整条计划并计数 `stat_pipe_rejected`。

顺带：这使管道计划成为 **L1 分解器的一个天然消费者**——但**不等 L1**。
fan-out 在没有 L1 的情况下由模型直接产出合法序列（§4.17.9 已验证），
管道同理：模型给出"我要这几步按序做"，类型图只做**校验**（close 那一关），
不做**构造**（构造权仍属算法，§4.6.3.1 的判据不破）。

### 2.3 计划的执行骨架：复用 WorkItem fan-in，零新容器

不新建 Plan 类型。一个管道 = **1 个头条目 + N 个子条目**：

- 头条目：普通 WorkItem（`pending = N`），就是现有汇聚机制；
- 子条目 k：`parent = 头`，完成时 result blob **不归还**，而是交接为
  子条目 k+1 的 args（复用 blob 池 handoff 语义，§3.1）；
- 子条目 k `FAILED` ⇒ 头条目**不判 FAILED**，置 PAUSED 态、记下断点
  `cursor = k`——这是与现有 fan-in 唯一的行为分叉，见 §3。

于是：DAG 推进、世代 handle、blob 交接、"失败不悬空"断言、信任天花板随
条目走（`WorkItem.trust_max`）——全部原样复用。计划的断点、计费、观测
在 SoA 里肉眼可查（白盒），不藏进模块 state。

**归还时机改动（唯一需要动的生命周期）**：管道模式下中间 result blob
活到**头条目终态**才整批归还。这与现有"单点归还"纪律不冲突——归还仍是
一处（头条目 RECYCLE），只是时机从"各子条目完成"推迟到"计划结束"。
同时 `blob_bytes` 白盒账自动覆盖"计划活着 = 中间结果占多少字节"。

### 2.4 断点反馈：断点处的事实摘要回模型

PAUSED 时向模型的下一次 prompt 携带（进 transcript blob，现有渲染路径）：

```
#plan paused at 3/5
#result fs.grep decrease-key 272B      ← 前 k-1 步照旧
#result fs.read 96B
#fail fs.write_new EEXIST                ← 断点步的错误，原有 #fail 格式
```

模型据此**补后续计划**（重发步骤 3..5，或改方案），或回 `DONE` 交部分结果。
注意这是"模型改计划"，不是"运行时替模型重试"——重试策略的决策权在模型，
因为"下一步干什么"是语义判断，落在 §1 判据的断管侧。

## 3. 执行语义：四行状态机，一处分叉

```
PIPE_HEAD:  BLOCKED(pending=N) ──子k DONE──▶ (k<N-1 ? 交接args[k+1] : 汇总)
                     │子 k FAILED
                     ▼
                  PAUSED(cursor=k) ──模型补计划──▶ 派生子 k'..N'（pending += 新条数）
                     │模型回 DONE
                     ▼
                  DONE（部分结果合法，stat_pipe_partial++）
```

不变式：

- **P2 不部分应用**（执行中）：步骤 k 失败，k+1..N 不启动。已完成的
  0..k-1 结果保留（断点资产），不是部分应用——部分应用指的是"假装
  整组都跑了"。
- **P3 头条目终态前，中间 blob 不还**；头条目终态（DONE / FAILED /
  PAUSED-and-abandoned）时整批一处归还，`blob_bytes` 归零可断言。
- **P4 断点续跑不重放前缀**：模型补计划时，前 k-1 步的结果**从 blob
  引用进 prompt**，不重跑 handler。幂等性由此不是硬要求而是白拿的——
  反正不重跑。（对比 codemode：脚本作废 = 全部重跑。）
- **P5 信任天花板随每步走**：计划不绕过门控。补计划的重发步骤重新过
  INJECT 的天花板挑选（分解期门控，§10.4），`stat_denied` 照旧可观测。

## 4. 与既有机制的关系（防重复造轮子清单）

| 机制 | 关系 |
|---|---|
| 轮内 fan-out（§4.17.9） | 管道是它的顺序化推广；共享"整批失败、≤8 条上限、单解码器"全部纪律 |
| TTN 类型图（§10.6） | 提供 P1 端口校验；管道成为类型图的**运行时消费者**之一 |
| blob 池 handoff（§3.1） | 步骤间交接复用同一套；唯一改动是归还时机 |
| WorkItem fan-in / pending | 计划头就是汇聚节点；PAUSED 是唯一新状态 |
| 停滞观测器（§2.1 观测层） | PAUSED 头条目**不计停滞**——它在等模型，不是没进展 |
| budget drop / query-aware（§4.15） | 照旧治理断点反馈的体积；N 步结果进 prompt 是主要字节账，P3 归还时机保证峰值可测 |

明确不做（各带触发条件）：

- **端口映射 / 具名引用**：等真实计划出现"只需要 result 的一部分"的
  高频需求（b* 指标说话）。
- **管道内条件分支**（"如果失败就换 B 能力"）：那是编排语义，属于
  L1/消解层，不是数据流。管道内分支一旦出现，说明该处该断管。
- **并行管道**（DAG 内并行支路）：多rank 之后再议；单 rank 下顺序
  管道已覆盖主要收益。
- **自动重试断点步**：重试与否是模型决策（§2.4），运行时只负责把
  事实摆齐。自动重试会把它变成策略，策略要可观测才能上。

## 5. 失败成本账（为什么这格比 codemode 划算）

同一份"读 → 变换 → 写"三步任务，第二步失败时：

| | 重放工作量 | 模型参与 |
|---|---|---|
| codemode 脚本 | 三步全部重跑 | 降级逐步后每步都要 |
| 管道计划 | **只重跑第 2 步**（P4），第 1 步结果从 blob 引用 | 只在断点处补一次计划 |
| 逐步 CALL | 不重跑（每步本就独立提交） | 每步一次调用 |

管道的位置是清晰的：它比逐步省 N-1 次模型调度和前缀，比 codemode
省"整块作废"。代价是**模型必须一次枚举对 N 步的顺序**——比写对一段
JS 容易（每步仍是训练过的 CALL 形状），比一步一猜难。所以这个档位
天然适合：**任务形状已知的批处理**（读三个文件拼摘要、清洗-转换-落盘），
以及**同一任务家族被反复执行**后由 flywheel 结晶出的模板（§7：
先脚本化的是流程，不是模型即兴写的代码）。

## 6. 谱系定位与落地次序

四档按"模型参与度"排，不互相替代：

```
并行批 fan-out（已落地 §4.17.9）
  → 管道计划（本提案，差两件小事：顺序消费分支 + 头条目 PAUSED 语义）
    → 逐步 CALL（语义衔接处，永远存在的默认档）
      → code.run（云端强模型可选优化层，需要 JS 沙箱件，独立决策）
```

落地清单（都很小，且全部落在既有文件里）：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `tests/agent.c` `inject_actions` | 解析层加"顺序消费"分支：端口匹配则串成管道，不匹配拒 |
| 2 | `tests/agent_types.h` | WorkItem 加 `cursor`（u8，断点位）→ **必须 `make gen`** |
| 3 | `tests/agent.c` RECYCLE | 管道子条目 result blob 延迟归还到头条目终态（P3） |
| 4 | `tests/agent.c` | 子条目 FAILED → 头 PAUSED（而非 fan-in 失败传播）+ 断点摘要渲染（§2.4） |
| 5 | `tests/test_agent.c` | 剧本式断言：P1 拒绝、断点续跑不重跑（步骤计数器钉住）、P3 blob 归零、PAUSED 不算停滞、部分 DONE 合法 |

**断言**（沿 §6.5 风格）：轮数 == 剧本长度；步骤 k 失败 ⇒ handler 执行
次数恰好 k（证明前缀没重跑）；`blob_bytes` 峰值含全部中间结果、终态归零；
端口不匹配的计划 `stat_pipe_rejected` 递增且一步未执行；收紧天花板后
补计划的重发步进 `stat_denied`。

## 7. 诚实边界

- **省的是调度与前缀，不是正确性。** 管道的错误定位能力弱于逐步式
  （模型看不到中间结果，只能靠断点反馈）。b*（§4.15 注意力分差）
  会告诉我们 N 步结果压进一次 prompt 的代价——若 context rot 显著，
  管道只该用于短链（2~3 步），这条由测量定，不由本提案定。
- **模型枚举错顺序的代价是一次拒批**（P1），不是静默错接——但拒批
  本身花一轮。τ 类参数（§4.6.2）成熟后，"何时值得出计划 vs 逐步问"
  才有校准依据；v1 不做这个判定，模型出计划就用、端口不接就拒。
- **与 L1 的关系是消费而非依赖**：管道是 L1 产物的一个合法形态，
  但 v1 由模型直出、类型图校验，与 fan-out 同路。等 L1 解禁
  （§10.7 第 1 项），计划可改由分解器构造，执行层不动。
