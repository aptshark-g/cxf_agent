## 每次改动怎样同步

| 改动类型 | 更新内容 | 验证范围 |
| --- | --- | --- |
| 接口／所有权／边界／策略 | 实施前更新对应设计契约；实施后更新现状、`docs/STATUS.md`、变更记录 | 与变更直接相关的正确性、失效／取消／资源边界；需要时运行真实模型 oracle |
| 兼容性或功能修复 | 写清触发条件、修复后行为、受影响的平台／模型、实际结果 | 功能验收单独记载，不能作为性能样本或自主能力分数 |
| 新性能实验 | 新日期／版本的 evidence 文件、新 ID、原始样本、源码／依赖哈希和限制 | 同组公平基线、相同工作量、重复样本、负结果；不得覆盖旧实验 |
| 只改说明／清单 | 更新相应说明与变更记录；历史实测版本保持原样 | 报告、链接、清单、发布包离线校验；明确没有复测推理 |
| 展示图或结论变化 | 同时更新中英报告、CSV／图表输入与方法；重新渲染并目视检查 | 数值追溯、范围／单位／样本数、限制与旧结论是否仍适用 |

“已实现”“宿主可调用”“默认 Agent 已接入”“回放通过”“目标平台已验收”分别写清。源码改了但尚未复测时，写“当前实现已变更，该项性能待复测”，不要把旧图表悄悄升级为新版本成绩。

## 数据登记与不可变约束

1. `docs/evidence/` 的已归档证据保持不变。补充／纠错也保留旧版，追加新版本并写明替代原因。
2. 在 `tools/build_benchmark_report.py` 的 `SPECS` 注册新数据集、证据等级、预期记录数及正式运行目录；同步 `load_evidence` / `data_products` 等需要的日期与格式支持。当前生成器对应固定快照，加入新轮次时必须更新这些入口。
3. 给新实验增加合适的原始记录统计、summary 校验与报告段落；不能只登记文件而漏掉结果。新增功能证据也更新验收矩阵。
4. 在 `tools/render_benchmark_figures.py` 更新受影响的图表与输入来源；图表 provenance 同时记录数据与渲染器哈希。
5. 根 README 和历史索引的记录数／结论、发布说明中的数量、报告生成器中快照名称及统计提示也要同步。现有 E01–E12/L01 编号和对应原始记录数不能为迁就新结果而更改。
6. 本地开发试跑不混入正式样本。`--refresh-inventory` 可更新仅含安全元数据的运行目录清单，并标明 superseded、失败／未完成与验收用途。

新试验至少记录：日期、硬件／系统／后端、模型／模板／引擎哈希、实测源码哈希、配置与容量、基线、工作量、预热／顺序／样本数、单位、原始样本、汇总、正确性、排除成本、失败／限制。准备阶段与完整任务耗时分列；保存与恢复成本分列；原文、ID、KV、临时堆与 RSS 分列。

## 本地更新流程

只有受影响图表需要重渲染；普通文档编辑不必重跑模型。先完成相应的功能或性能验收，再更新其文档，最后重建展示资料：

```sh
# 有新性能数据：按对应 runner 运行到新的 build 目录，脱敏后追加 evidence
# 图表有变化：使用已安装 ReportLab 的 Python
python3 tools/render_benchmark_figures.py

# 文档／清单／证据有变化：更新派生文件与发布哈希
python3 tools/build_benchmark_report.py
python3 tools/build_benchmark_report.py --check
python3 tools/build_benchmark_report.py --check --export build/cxf-benchmark-results-20261101-test-sandbox-host.zip
```

渲染器改变或图表引用的 evidence 改变时，check 会拒绝旧 provenance；报告、CSV、发布文件哈希或包内链接／标题锚点过期时也会拒绝。当前检查覆盖归档统计与数据包，无法自动证明所有实现说明仍正确；实现状态仍需逐项核对源码与测试。

发布包只包含白名单成果资料。首次上传 GitHub 前仍另做全仓库清理；维护文档和离线包不执行 Git 提交／推送，也不创建定时任务。
