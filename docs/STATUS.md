> **测量顺序 p → N → k 不能反**：下一刀是 `stat_batch_rejected` / `stat_batch_ok`，不是 `#notrun`。

### 1.1 内核成熟度：形状收敛，验证停在"单线程 + 剧本负载"

内核 5 件事逐项（**接口已定，不会再改签名**）：

| 职责 | 落地 | 缺口 |
|---|---|---|
| 内存 | `alloc`（唯一函数指针点）+ `arena`（chunked + 帧栈） | 只有 heap backend 一个（池 / 共享段 / 越界检测明确不做） |
| 标识 | `handle` = index 32 + gen 32，typed class 占 gen 高 8 位 | 无 |
| 存储 | `table`（稀疏集）+ `soa`（列式）+ `layout`（type-tree 展平） | 无 |
| 通信 | `ring`（SPSC，`head`/`tail` 各占一条 cache line，`_Atomic`） | **全仓库唯一用 atomics 的地方，却没有任何线程测试** —— 内存序未被验证 |
| 调度 | `world`（registry / phase / tick / 帧 arena / `phase_ns[]`） | 单线程顺序跑 phase（设计如此）；`cxf_module_unload` 有，但**服务与类型没有 unregister** |

**"差不多了吗"的准确答案**：接口差不多（§4.8 多轮闭环落地时内核**零改动**，只动 agent 层 —— 这是"内核能承载没预想到的用法"的强信号）；工程成熟度不满，最实的四条缺口是
① ring 无并发测试 ② tick 无并行 ③ **能力只能"插"不能"拔"**（`world.services` 与 agent 的 `cap_count` 都只增，`registry_sync` 的 `scanned` 游标只前进）④ ~~只有一个真实消费方，且它的能力实现全是 mock~~ → **真实实现已开出 6 个（fs 族 5 + 出网 1），而静态 bundle 里那 6 个仍全是 mock**（2026-10-21）。

> ③ 是**文档承诺与代码落差最大的一处**：多处写"能力热插拔"，实际能做到的是"热插"。拔需要删服务项 + 让游标失效 + 走 §6.3 不变式 7 的对称项（删边查孤岛），三件都没做。

所以准确的说法分两句：
**测试里**骨架、协议、执行层都是真的，载荷此前全假，现在有了第一条真的；
**`agentctl` 里**连模型与端点都是真的 —— 于是"答不答对 / 调几次工具 / 会不会打转"
第一次成为可测的量（§4.16.3 的实测表就是它的第一批读数）。
模型那里仍有假的一格：`test_llm.c` 的对端是 `loopback.h`（回放写死 JSON），
它测协议，不测模型 —— 两件事分开是刻意的。

**⑤ 工具结果没有回流路径 —— 已补（§4.16.1，v1.7）。**
现在的准确说法是"**能调用、能真执行、结果回到发起调用的那一行**"：派生时若工具是终态
（`cap_acts[cid] == false`），原控制流条目**就地**改成续跑节点 `S'`（`status=BLOCKED`、
`pending=1`、`rounds+1`），工具结果的 `parent` 指向它 ⇒ 结果 append 进 `S'.args` ⇒
`pending` 归零 ⇒ 下一轮模型拿"原 args + 工具输出"再问一次。
"就地"这个选择消掉了一整类所有权问题：`args` 转移这个动作根本不存在，也就没有"谁 free、
失败怎么退回"。
> 当年那条根因记在这里留着：**控制流派生要"父节点消失"，数据流汇聚要"父节点存在"** ——
> 两个方向的需求顶在一起。§4.8 选了前者（正确，否则半成品会被当最终答案），
> 代价是工具输出失去默认接收者；补法是让 `parent` **只承担同轮数据流**，
> 而跨轮 lineage 继续由 `rounds` 承担（两者刻意是两个字段）。

## 3. 已定，不再讨论（列出来防重复推演；共 51 条）

1. 内核只做 5 件事：内存 / 标识 / 存储 / 通信 / 调度。日志 / 配置 / 统计 / 错误一律 SOFT。
2. 白盒优先：结构体公开、无 opaque pointer、热路径不用函数指针多态（改 switch 内联特化）。
3. 热路径零分配（显式 allocator + arena 帧）；**无回调**（显式 tick phase）；**无全局单例**（一切挂 `world *`）。
4. 三层分类：**结构**（拿掉它不自洽）/ **算法**（自洽但缺一种变换）/ **契约**（结构没事，用法失去保证）。
5. **没有真实调用方不进库。** 已实证：§4.8 落地**零新增结构**（`acts[4]` 定长、`cap_acts[16]` 用 bool 不用 bitmap）。
6. 三阶段纪律：装配期查找 → 固化期缓存 → 调用期零查找。度量用内核槽位 `service_find_count` / `type_find_count`，不自造计数器。
7. `vec` 是**增长策略的唯一实现**；**两个值必须一起变，就让它们同住一个结构**；**释放用的 size 必须是申请时存下的值**（不能事后从可变状态重算）。
8. string 三段路线：① schema 前移（首选）② intern ③ 规模上万再换哈希。**明确不做 SSO / 拥有型 string**。判据：**热路径上出现字符串操作 = 设计错误的症状**，能删掉的优先于能加速的。
9. **字节搬运不是瓶颈**（实测占 0.5%，差 2~3 个数量级）。要动的是**重复执行 handler**，不是 string。
10. `agent.action` 是**接口类型**（方案 D）；**控制流条目在 RECYCLE 不回收**（交接一行所有权）；**`parent` ≠ `rounds`**（同轮 fan-in vs 跨轮 lineage）；**动作里的名字是切片不是 C 串**。
11. 未加载模块在图里是孤立点 ⇒ `cxf_algo_toposort` 判全图与旧 Kahn 判 loaded 等价。**若允许边指向未加载模块，这个等价就破。**
12. 生成物只写表达式（`sizeof`/`_Alignof`/`offsetof`），**绝不写死数值**；生成物进版本库、生成器不进构建（`make gen` 手跑）。
13. **"成熟"的判据不是用例通过，是任意操作顺序下不静默错** ⇒ 模型对照随机序列 + 三构建同跑。
14. **观测层的判据是"判推进，不判完成"**：以完成为判据会把所有长任务误判成卡住，那种计数器上线即废。
    停滞阈值必须跟着业务上限走（`(AGENT_MAX_ROUNDS+1)×2`）而不是写死 —— 写死会在调大上限后变成误报源。
15. **有界可以，静默不行**：`AGENT_FINAL_MAX` 允许存在，但超限必须计数（`stat_final_lost`）。
    同理 `AGENT_ACT_BATCH` / `AGENT_MAX_ROUNDS` / `AGENT_RESULT_TRIES` 超限一律走失败路径 + 计数器。
16. **结构化停顿优先于行为化停顿**：A4（`pending` 必须等于活子项数）能当场判定的，
    不要留给"跑 K tick 没动静"去猜。前者是结构，后者是症状。
17. **能力实现不许读文件级全局**：端点 / 密钥 / 超时由描述符的 `ctx` 显式传入（`CapImpl.ctx`）。
    "这个 handler 连了哪里"必须是注册期事实，不是翻源码才知道的事。一个进程一个端点，
    多端点 = 构造两份描述符。
18. **输出长度不可预测的实现，起始容量在注册期声明**（`CapImpl.out_hint`）。
    容量不足触发的是**重跑**，而重跑的返回字节不保证与第一次相同 ⇒ 那是正确性问题不是成本问题。
    实测：同一份 700 字节响应，`out_hint 8192` 请求 1 次、`0` 请求 4 次，且起始容量不足可以
    把一次本可成功的调用变成 FAILED（四跳已接近 `AGENT_RESULT_TRIES = 5`）。
19. **文本动作的语法是"头一行 + 体原样"**，不是 JSON：`CALL|<cap>\n<args>` / `DONE\n<payload>`。
    理由是转义的必要性 —— 一旦要转义，读写两端就得有两份对称的解码器，不同步的表现是
    "某些参数被静默截断"。把"头"缩到一行之后体是纯载荷，转义的需求消失。
    解析器**不自己拼头**（走 `agent_act_encode` → `agent_act_decode`），所以布局只有一个正本。
20. **模型到动作的转换落在 handler 里，不落在运行时**（与 `ctx` 同构：谁知道背后的东西，
    谁负责）。于是 `CapImpl` 不必为"格式可靠性"加字段，RECYCLE 一行不改；而失败确实响亮
    （`FORMAT` ⇒ 条目 FAILED + `stat_failed`），缺的只是**归因**，那属于每实现健康度（§5.3）。
    三种错必须分开报：`FORMAT` 重试没用 / `RANGE` 设计边界 / `FULL` 唯一该扩容的一种。
21. **清单走协议、动作走文本**（§4.16）：工具清单必须结构化（`tools` 字段），动作表达保持文本
    （`CALL|<cap>\n<args>`）。判据是**两件事的消费者不同** —— 清单是模型每轮都要读的固定前缀，
    动作是我们要解码的一次事件。附带两条硬约束：① 每个工具只有**一个字符串参数 `args`**
    （否则解码器数量随工具数线性增长，违反第 19 条）；② `tool_calls` 必须译回同一份文本
    再校验，**下游零改动、解码器仍只有一份**。
    抓包实测补一个尺度：tools 定义 54–84 KB，是固定前缀的**最大单项，比 system 还大**。
22. **拆分单位是"语义闭环"，不是"运行时记账闭合"**（正本 `l1-decomposer.md` §2.5）。
    后者每个 row 自动成立（都有 `parent` / `pending` 归零 / 终值）⇒ 按它拆等于没约束。
    语义闭环三条：独立验收 / 独立重跑且代价可声明 / 副作用同生共死。
    拆分的下界 = **写操作的原子边界**，上界 = **目录里没有能力能整体承接**。
    **责任只能在分解期**：运行时的 `pending` 在子项失败时也递减（否则永远等不到 S'），
    所以它分不清"失败一条但语义仍完整"与"失败一条导致语义残缺" ——
    **`pending` 会掩盖分解错误，不会暴露它**。
23. **可逆性不是操作的内禀属性，是"恢复所需信息在不在系统里"**（正本 `l1-decomposer.md` §2.6）。
    判据一条：`可逆 ⇔ 存在逆操作，且执行它所需的信息在正操作完成后仍然存在`。
    ⇒ 读可逆 / 写自己创建的新路径可逆 / **覆盖与删不可逆**（旧内容已消失，除非有版本库·快照）/ 出网不可逆。
    三句流行说法都是错的：**"单行为安全"**（单个 `write` 覆盖配置就能让服务起不来）、
    **"删能复原"**（`rm` 在 git worktree 里可逆、在 `/tmp` 里不可逆 —— 那是存储系统的属性）、
    **"组合才有风险"**（组合的两种风险是"半完成"与"权限合成"，后者与可逆性无关）。
24. **`trust` 是能力级属性，而风险是数据级 / 目标级 —— 同一处根因，两种表现。**
    ① **挡不住组合**："读敏感 + 出网写 = 外泄"，两个能力各自都合法，数据流向仍然非法。
    **不加第四级 trust**（那还是能力级）；要的是**污点标记**（LOCAL 读出的字节不得进 IO/WRITE 的入参）。
    ② **挡不住"写到哪里"**：`CapImpl.trust` 是**常量**，而写同一个字节到 `docs/` 与写到
    `~/.zshrc` / `.git/hooks/*` / `Makefile` / `crontab` 是**延迟执行**，风险差好几个数量级。
    常量只能取最高级（于是天花板必须开到 WRITE = 门禁失效）或取平均（于是高风险的漏掉）。
    **解法不加新结构**：`ctx` 随部署来 ⇒ 一个 `fs.write` 描述符绑定**一个 root**，
    该 root 的信任级由部署声明；要写第二片根就注册第二个描述符，天花板自然挡住。
    **两者现在都零代码且不该建**：目录里没有出网写能力，也没有任何写能力 ⇒ 没有真实调用方，
    约束会写成"永远成立"从而永不被验证。触发条件 = **第一个写能力落地，同一个提交**里加。
25. **四层边界，只有两层该写在这份代码里**（正本 `agent.md` §4.18）。
    **分层不是优点，除非每层的违约能在这一层判出来** —— 一个"层"的全部内容就是
    **一行只用到本层信息的谓词**：`realpath(target) ⊂ root`（L2）、`taint(src) ⊆ allow(dst)`（L3）。
    三条推论：① 不能自己判定违约的"层"只是注释（"有安全意识"/"prompt 里写了"都不算）；
    ② **多层挡同一类 = 只算最内层**，各挡一类才是纵深（重复挡的那层测试永远绿，安全感是假的）；
    ③ **层的边界 = 谁负责的边界** ⇒ L4/L5 不进仓库不是不重视，是"主语不是我们"。
    L0 契约（模型表达不出来）/ L1 调用准入（表达出来但不许调）**已有**；
    L2 参数准入 / L3 数据流**归我们、零代码**；**L4 OS 强制 + L5 可逆性不进仓库**。
    **顺序是先 L2/L3、后 L4**：进程级沙箱对进程内的信息流是瞎的
    （`fs.read` 读出密钥、`http.post` 送出去，OS 只看得见 socket 被打开）。
26. **契约的来源必须比契约本身更可信。** 出处是 Codex 的 CVE-2025-61260（CVSS 9.8）：
    仓库里的 `.env` 把 `CODEX_HOME` 重定向到项目内 `.codex/` ⇒ CLI 自动加载并执行其中的
    MCP 条目，无审批。根因不是"解析有漏洞"，是 **trust is resolved at the config location,
    not at the config contents**。映射到 cxf：`registry_sync` 现在读的是**编译期 bundle**
    （`tests/agent_caps.gen.c`）⇒ 安全，但这是"恰好如此"不是不变式。
    **判据（注册期，不是部署纪律）：契约的来源必须在 workspace 的可写根之外。**
    "能力由谁定义"不能落进"能力能写的地方"。
27. **`ctx` 是隐式入参，凭据装进去就必须保证它没有任何一条路写进产出。** 触发条件
    （"第一个需要凭据的出网能力"）**已在 2026-10-21 兑现**，而兑现的方式**推翻了这个条目
    原来的措辞**，所以措辞要跟着改：`http.post` 的凭据**就在 `ctx` 里**（`HttpCfg.auth`，
    来自 `CXF_NET_AUTH`）—— 没有别的通道，"只装部署事实"这条在字面上守不住。
    改写后的口径按"**能不能漏**"判，不按"在不在"判，而"能不能漏"靠三个结构事实：
    ① 不从 payload 来（方言只有 `path\nbody` 两段，没有第三段可塞）；
    ② 不回显进收据（收据是 `<status> <b>`，与凭据无关）；
    ③ 不进输出缓冲（缓冲里只有状态码与响应体，凭据不参与拼接）。
    ⇒ **原判据（"ctx 类型里出现 key/secret/token 即拒绝注册"）是错的测试**：它拦住的是
    一个**合法部署**（凭据只能来自部署侧），而真正该拦的"凭据进 prompt / 进日志 / 进 KV cache"
    它一条也没看到。Codex 那件事真正说明的是"**隐式入参会漏**"，不是"隐式入参不许存在"。
    **残余缺口（没有闭合，如实记）**：三个"不"目前只由**代码事实 + 一条测试断言**
    （凭据不在 body、不在收据）保证，没有注册期谓词能判它。**下一个凭据能力落地时，
    要么把这三个"不"收成一条可复用的不变式，要么找出判不了的实例** —— 那才配写进宪法。
28. **目录形状是"条数 × 每条自由度"两个轴，不是"少而精 vs 多而全"**（正本 `agent.md` §4.18.4）。
    Unix 的位置是"**很多窄接口**"（正交 = 语义不重叠，不是数量少；POSIX 几十个工具）；
    PowerShell 的 verb-noun 反而是正交的显式编码。
    ⇒ **加新能力的正当理由不是"它能做一件新事"，是"它引入了一个新的自由度维度"** ——
    `fs.grep path` 引入了 path 这个维度（该加）；`fs.grep_todo` 只是 preset 的 pattern（是 alias，
    该沉进蓝图）。把"预设参数"当"新能力"就是目录膨胀而模型能用错的地方一个没少的病根。
    **第二笔预算**：条数线性推高**固定前缀**（4 个能力 `tools` 1477 B，真实抓包 54–84 KB，
    且在 KV cache 救不了的头部）⇒ 条数与自由度一样，只该花在"新维度"上。
    **两种味道在一起的方式是"在同一个能力内部"，不是"在目录里"** ——
    **实现可以复杂，契约必须窄**（`fs.grep` 实现 244 行，契约一个 pattern）。
    蓝图是窄接口的**后果**（窄 ⇒ 组合必然 ⇒ 需要声明/检查/复用），不是它的替代；
    **顺序是 L0 纪律 → 组合 → 蓝图**。
29. **出网能力的四条不变量**（`http.post` 落码时定，再想问就引这一条）：
    ① **永不 `FULL`** —— `FULL` 的框架语义是"再给一倍、把 exec 从头再调一次"，对出网就是
    **再发一次请求**（对方收两次、按次计费、副作用不可撤）⇒ 响应超限报 `#truncated` + `CXF_OK`，
    我方容器不够报 `RANGE`（宁可失败也不重发）。**契约的目的不是"让重跑安全"，是让重跑走不到。**
    ② **凭据的三个"不"靠结构而非检查** —— 不从 payload 来（方言只有 `path\nbody` 两段，没有第三段
    可塞）、不回显进收据、不落进输出缓冲。检查会漏，结构不会。
    ③ **收窄自由度代替黑名单** —— host·port 来自 `ctx`（部署事实），模型只给 path；与 `fs.*` 的
    "根从部署来、路径从模型来"是同一个谓词在两条轴上的两副面孔。黑名单挡不住 `//evil.example`
    这种（实测第一版就漏了：斜杠合法、`..` 检查不触发）。
    ④ **5xx 不映射成错误码**（`<status> <b>` 原样）—— "对方拒绝我"与"我没问出口"混成一件，
    下一步该做的事相反；而协议层的 `truncated` 由**产生处**标记（"body_len 恰好等于容量"与
    "body_len 是真实的全部"在能力层眼里一样，这个事实只能在产生处判定）。
30. **同族计数器只准有一个口径：凡是钱 / 出网 / 重试，一律按实际调用计**（A3，2026-10-21）。
    `stat_cost` × `stat_llm_calls` × `stat_exec_calls` 三件同口径，于是
    `stat_exec_calls − stat_executed` 的**差值**就是浪费量 —— 一个数同时回答
    "花了多少钱"和"其中多少是白花的"。**报"条目数"的计数器在这里一律是错的**：
    低报会给出"这个回路很便宜"这种看起来成立的结论（实测低报 2.7×）。
    配套两条：断言**钉差值不钉绝对值**（换 handler 后仍成立的才是不变式）；
    **判死一个字段用 grep 不用推演**（`CapRerun` 四轮没定案，一次 grep 给出"零行代码"）。
31. **按字节切的东西，切口必须落在字符边界上**（`utf8_clip`，2026-10-21，v1.14.7）。
    这是第 15 条"有界可以，静默不行"的第三个实例，且比前两个毒：前两个坏的**是数量**
    （`#truncated` / `#fail` 至少数是对的），这个坏的**是字节本身** —— `fgets` 在 511 处
    硬切，一个 3 字节汉字的引导字节进了上下文、后续两字节丢了，进请求体 JSON，
    宽宏大量的服务端照收、严格的直接 400，而能力层报 `rc=OK` 一个标记都没有。
    ⇒ **判据分两层**：① 超长行只给首段是可接受的设计（界），② 但切口必须退到最后一个
    完整字符边界（静默）。修法三条边界：不猜不修坏字节（引导字节非法按长度 1 放过）；
    病态输入（连续 4+ 续字节）原样返回，不因"修不了"把整行吃掉；只动切口不动行号规则。
    测试形态：**断言字节本身合法**（整串输出是完整 UTF-8 + 行内容长度精确等于 pre），
    不是只断数量 —— 这是本仓库第一个这类用例。同源未决项：`#truncated` 报行数而切的是字节。
32. **"我改了但行为没变"之前，先证明二进制真的变了**（2026-10-22，v1.14.9，本机沙箱实测）。
    文件写入 / `os.utime` / `os.remove` 都被 WorkBuddy 沙箱代理**延迟**：变异写进盘了、
    回读校验也过了，但 make 按 mtime 判断不重建 ⇒ 跑的仍是旧二进制 ⇒ **假绿**。
    同族三症状：还原后 make 不重建（变异留在二进制里，污染下一个用例）、touch 不触发重编、
    删 `.o` 不生效。解法四件套（`tools/mutate_check.py`）：写后回读校验 + `make -B` 强制全建
    + **二进制 sha256 前后必须变**（没变 = 没建进去，重试）+ 还原后自检。
    **判据**：凡结论是"改了没生效"，先证二进制变了再信；GREEN 先怀疑构建竞态，再怀疑测试空白
    （本轮一个变异两者都发生过：M5/M6 是竞态，M10 是真空白）。
33. **手数字节数必错，用程序自身输出反算校准**（2026-10-22，同一轮连错三处）。
    `TOK_05` 少数一个字符 ⇒ 记录 74 算成 73、`bytes_lost` 74 写成 75、断言头 `fs.grep 5` 应为 6。
    判据：blob/记录长度这类数，**先跑一遍让程序打印，再拿打印值写断言**；
    反过来用手算值写断言，红的时候分不清是实现错还是算术错。
34. **表达空间是"闭包"，不是各能力表达空间的和**（2026-10-22，v1.14.10）。
    `fs.write_apply` 单独看只是"改一个文件"；配上「`make` 读 `Makefile` / `git commit` 跑
    `.git/hooks/*` / `npm ci` 跑 `postinstall` / `pytest` 导入 `conftest.py`」就变成**写代码**，
    而**执行者不是我们**。⇒ 「沙箱强度匹配表达空间宽度」要按闭包算：
    ① 契约层准入看不见（谓词只答"在不在 root 内"）；② OS 隔离也挡不住写入（写入合法）。
    L4 的作用因此不是"防越权"而是**压爆炸半径**，在某些部署里是**准入条件**而非可选加固。
    同族两条：**默认拒绝改带执行位的文件**（`write_apply` 保留旧权限位是正确设计，代价是
    它能把已存在的可执行文件换成模型写的代码）；**可写面由部署声明**（可写子树，默认空），
    不用黑名单 —— 黑名单（`.git/`、`node_modules/`）永远漏。
35. **准入是"逐层合取"，不是"跨层取最小值"**（2026-10-22，v1.14.11）。
    默认形状 `天花板 = min(部署档, 模型档, 可回溯性, 索引判定)` 是错的：它让某一维的缺失
    **传播成所有层都不许**。只读层没有副作用，"可回溯"对它无意义 ⇒ 一个无关维度的缺失
    关掉了一整片能力。正确形状是每层一组合取式，`model_tier` 只出现在 `need(L) > 0` 的层
    （L0 读对任何模型档放行）。这是 §4.18.0「每层一行谓词」的第四条推论 ——
    **层怎么分**它讲了，**层的准入怎么组合**没讲，而默认答案恰好是错的。
36. **准入判据必须可复现 ⇒ LLM 不能进准入路径**（同上）。
    「可归因」的第一要件是"同一输入两次得到同一判定"。LLM 生成的拒绝理由不满足这条，
    于是"理由"退化成一段看起来很有道理的文本。LLM 只能出现在**非准入**位置（事后审计 /
    给模型的自查提示），产出是**证据**不是**判据**。
    ⇒ 这把既有的"LLM 只做 zero-shot 先验分类器"**收窄**了一次：先验可以做，先验不能当判据。
    同族两条：**索引版本要进收据**（`(能力名, bit, 索引版本)`，否则三个月后没人知道它在拒什么）；
    **命中不必然拒绝**（`SUS_EXEC_SURFACE` 拒绝；`SUS_VOLUME` 转配额闸门 = 资源型可等待；
    `SUS_SECRET_SHAPE` 只给产出打标 —— 拒绝它会误伤 `fs.grep` 命中一行含 `sk-` 的正常文档）。
37. **"只读"不等于"小权限"：读面宽度由 `root` 决定，不由能力决定**（同上，本轮自查发现）。
    `fs.diff` 给空 content 时**每一行都是 `-`**，输出即指定文件的全文（`agent_fs.c:697`）⇒
    只读部署挂 `--diff` 拿到的是**整库可读**，不是"差分摘要"。这不是漏洞（是 diff 的定义），
    但它与 §3-34 合起来给出对称的一条边：**读 × 出网 = 外泄**（`fs.diff` 读全文 + `http.post`
    发出，两个能力、零脚本）。⇒ **准入不能逐能力判，要判"这一对是否同时被授予"。**
    判据：描述一个能力的权限时，"能读/能写"这个动词不够，必须带**边界量纲**
    （读=root 路径集合 / 写=可写子树 / 出网=对端集合 / 执行=进程视图）—— 四者量纲不同，
    压不进一个 `CapTrust` 的序。**同一个 trust 值下面是不同量纲的边界，这是三档不够用的真原因。**
38. **条目该合并，但决定边界的是可逆性与收据，不是字节账**（2026-10-22，v1.14.12）。
    提案"给最强权限、越权就降级往复"方向对，但三处落点要挪：
    ① **不需要往复** —— `chain_pick`（`agent.c:278`）在分解期就按 `trust_max` 取第一个够得着的
    实现，**同一轮内**完成；往复只是花一整轮 LLM 调用去买框架免费做的事（且弱模型读不懂拒绝
    理由，会反复试同一个）。② **省的是卡片数不是权限**，而 `cat_count` 与 `cap_count` 共用
    一个 `CAP_MAX = 16`（`agent.c:215` / `:256`），**实现槽更紧**；且 `fallback` 是单指针
    （注册期不变式"每个能力恰好一个链头"）⇒ **一个弱档只能服务一条链** ⇒ 合并上限只有 1 张卡
    （`fs.write` = `diff`→`apply`）。③ **徽标 `script|llm,io` 只对强模型有信息量**，
    对弱模型是噪音 ⇒ `trust` 过滤不能取消，它就是"帮弱模型缩小选择面"。
    **字节账（实测，`agent_llm.c:535-556` 逐字面量算）**：一张卡固定 JSON 脚手架 **203 B ≈ 41%**，
    `in/out_schema` ~23%，`desc` 只占 ~16% ⇒ **减条目是唯一能省掉那 41% 的办法**，压文案只省
    一成六。~~我最初写的是"压文案比减条目省得多"，写完核一遍数据反过来~~ ——
    判据：**"少而精 vs 多而全"必须逐字节算到固定开销那层，靠直觉会算反。**
    但**能不能合不由字节账决定**，由第 39 条与可逆性边界决定；字节账只回答"合了值多少"。
    **合并的边界是"可逆性"，不是"语义相近"** ——「已存在时拒绝还是覆盖」是意图不是强度
    （做成参数就撞"加参数 = 新能力"那条）。
39. **条目可以合并，收据不能合并**（同上）。合并后落在弱档时收据是 `diff 16 15 +1 -1`、
    落在强档时是 `wrote n`，**两者必须保持可区分** —— 否则模型说"写这个文件"、我们只给了差异，
    它以为写成了，接着基于"已写入"做下一步 = 最坏的一类静默错。
    ⇒ **一个能力允许多个强度，当且仅当它的收据能说出实际落在哪个强度上。** 不满足时宁可不合。
    同族：§3 那条"我这次没做"必须能当场说清（靠收据，不靠重跑）。
40. **折叠（fold/unfold）改的是复杂度的阶，不是常数**（2026-10-23，v1.14.13）。
    提案"不只是省，是折叠 + 展开：工具不都被调用，多余的是开销；需要调用就展开，否则使用面不足"。
    平铺成本 = `轮数 × 能力数 × 卡字节`；折叠后 = `1 次展开 + 轮数 × 展开数 × 卡字节`
    （4 轮任务 21.6 KB → 4~8 KB）。**省的是乘法项**：一个只用 2 个能力的任务，平铺 11 个就是
    9 张卡的浪费，且每轮重付一遍。三条硬约束：
    ① **展开必须 append-only（单调、不回收）** —— 目录每变一次前缀就变一次，KV cache 全数失效
    （`agent_llm.c:493-499` 已写死）；与 args blob 的 prefix-stable 是同一条纪律。
    ② **前缀缓存边界是第一个要裁决的** —— tools 今天在进程启动时渲染一次（`agentctl.c:517`，
    static ⇒ 天然稳定）；折叠要求每轮重渲 ⇒ **稳定区只能放固定域名入口，展开出的叶子必须进缓存
    边界之后**，否则省下的字节用缓存赔回去。
    ③ **猜错工具名就是免费的展开请求** —— 折叠态下模型直接猜 `fs.write_apply`，未命中即它在告诉
    我们需要哪个域；拒绝理由从"错误"改成"该域已展开，下一轮可用"。⇒ 那次往复不是浪费，是折叠
    方案**唯一必要的一次往返**，且由模型真实意图驱动，比框架预测准。
    连带结论：**折叠不解除 `CAP_MAX = 16`，但它是扩容的前置条件** —— 上下文成本不再随能力数
    线性    增长后，cat 放到 64 才有意义（先折叠、后扩容）。与 §3-38 的合并**正交**：
    合并减"注册了多少"（解容量），折叠减"这轮用几个"（解上下文）。
41. **折叠省的不是缓存，是窗口与计费；缓存是折叠新增的成本**（2026-10-23，v1.14.14）。
    用户纠正："不是放在最前破坏前缀的，我们是放在最新的地方，这个是要考虑清楚的，
    否则我们省下那点缓存就白费了。"⇒ 三个资源必须分开，混成一个"缓存"会连"有没有省"都判错：
    **prefill 计算量**（缓存命中决定：平铺首次一次、之后全命中；折叠每次展开后重算一次前缀）/
    **窗口占用**（每轮实际 token 数决定）/**计费 input token**（token 数 × 单价，命中部分打折**不免费**）。
    ⇒ 折叠省的是后两个（乘法项），新增的是第一个（`O(展开次数)` 的一次性）。
    **判据：展开次数 << 轮数 ⇒ 净赚**（典型 轮数 4~8、展开 1~3）。且失效点选得巧：
    展开发生时正是模型还不确定要用什么的时候，那一刻前缀本来就没多大价值。
    两条已定的形状：① **"放最新处"不能在 JSON 字段层解决** —— `agent_llm.c:493-499` 已写明
    token 顺序由 chat template 定（模板总把 tools 渲染在 messages **之前**）、不由字段序定；
    必须在内容层：目录分两份，`tools` 追加式（给协议）+ 叶子进**最后一条 user 消息**（给模型看），
    与 §4.16「清单走协议、动作走文本」同构。② 三候选中选 **B**（追加式 + 文本一份）：
    A（叶子只走文本调用）会推翻 v1.14.9 刚落码的标准 messages；C（每轮全量重渲）丢掉 append-only、
    失效退化成 `O(轮数)`，三者最差。
42. **KV 缓存命中率是架构判据，但今天只守得住一半：确定性有测试，命中率零观测**（2026-10-23，v1.14.15）。
    已落地的六条不变式全在我们这边：目录按名排序与注册顺序无关（`agent.c:891`）、渲染是纯函数

43. **堆叠式生成：段的边界必须是"前缀可判定"的；回退要拆生成/执行两轴**（2026-10-23，v1.14.16）。
    用户要的形状：一次产出多段、**错只影响后缀、前面依旧可用**、且**可以回退** ——
    同时拿到"整轮的少次数"与"轮次的可回退"。两条硬判据：
    ① **前缀可判定性**：段的边界必须落在"不看后缀就能判定合法性"的位置。代码已具备一半
    （`agent_action.h` A4「每块的结束位置由它自己的头决定」，v1.13 头 5→9 字节）⇒ 任意前缀合法。
    **反例**：端口类型匹配天生不是前缀可判定的（判第 k 步接不接得上要先知道第 k+1 步是谁）
    ⇒ 这就是 `pipe-plan` P1 选错层面的深层原因，不只是换层，是换**可判定性类别**。
    ② **回退拆两轴**：生成可回退（无条件，纯字节删除）/ 执行可回退（受可逆性限制）。
    回退点不能越过最后一个不可逆副作用的段；`rewind` 必须带收据说清"哪些已经发生了"。
    **断点（必须写明，否则会被按 Spark 语义误用）**：RDD↔段 / lineage↔派生 / checkpoint↔blob /
    分区重算↔回退只重发 k..N 四组映射都成立，但 Spark 的 recompute 是**确定性**的，
    我们的"重发"是**模型重新生成** ⇒ **不是 recompute 是 retry** ⇒ 只保证
    「不重复副作用 + 结果可对账」，**不保证最终一致**。
    ⇒ 回退粒度 v1 取**动作边界 = 段边界**（最细、最自然、零新参数），
    等 `blob_bytes` 峰值 × 回退重发字节量出来再谈合并。
    ⇒ 对 §4.18.13 的反哺：**生成可分段是折叠展开的前置条件** ——
    生成整块不可分 ⇒ 展开只能发生在块边界 ⇒ 折叠粒度被生成粒度锁死。
44. **失败回执：位置归运行时，归因归模型；只报过去时，不报计划**（2026-10-23，v1.14.17）。
    用户问"反馈给 llm 哪些成功了、得到了什么、哪里开始失效"。核完代码四条：
    ① **"哪里第一次没成功"运行时可判（`rc`+`cap_id`，可复现）；"哪里开始错"只有模型能判**
    —— 静默错误里第 3 段把路径写错、第 2 段"成功"但结果已错、第 4 段才失败，
    运行时看到的是"第 4 段失败"，永远说不出"第 3 段开始错"（**运行时不判语义，也不许进归因**）
    ⇒ **运行时给下界，模型给上界**。
    ② **反馈的格式在教模型怎么改**：前缀已是 `#result`（事实）⇒ 模型自然只写后缀；
    散文式反馈 ⇒ 模型整篇重写。**想让"错只影响后缀"发生，反馈必须先长成堆叠的形状。**
    ③ **`#fail <cap>` 今天是真实缺陷，不是可读性问题**：`recycle_tick` 倒序遍历
    （`agent.c:2163`）⇒ blob 记录是**派出序的倒序**，而同名能力两条动作一成一败时
    `#fail <cap>` 无法配对，且"配对靠顺序"这个隐式契约从没测试钉过 ⇒ 必须带 `seq`；
    `err` 也必须带（`FORMAT`/`RANGE`/`FULL`/`DENIED` 四种错的下一步动作**相反**，
    今天模型只能盲试）—— 这是既定判据「三种错分开」的兑现点。
    ④ 新增只需三行共 **53 B**（`#fail` 28 / `#notrun` 12 / `#rewind_min` 13）；
    对照：三行"逐段成功清单"**也 53 B 但信息更少**（无位置配对、无错类、与 `#result` 重复）
    ⇒ **报清单是同样字节买更少信息。**
    **两条判据**：**回执只描述已发生的事实，不描述计划** —— 总数/剩余/进度在模型重写后缀时
    立刻失真，所以回执必须是"过去时"；**位置归运行时，归因归模型**，两侧都不越界。
    配套三条：失败**短路**（继续跑 = 白花钱 + 可能产生副作用 + `#notrun` 连续后缀消失，
    但这只对串行段成立 ⇒ **管道语义 = 串行是前提**）；`#rewind_min` 由**逐能力可逆性**算
    （`CapTrust >= WRITE` 只是近似：`fs.write_new` 可逆、`fs.apply` 覆盖不可逆）；
    报"得到了什么"只载入**失败段的输入邻域**（上游 1~2 段全量 + 更早各段收据），
    且**只有段化之后"邻域"才可定义**。
    **Spark 第二个断点**：第一个是 retry ≠ recompute（第 43 条）；第二个更致命 ——
    **它的 lineage 由调度器按真实依赖构建、可信；我们的 lineage 是模型声明的、可能一开始就错**
    ⇒ Spark 里"重算失败分区"是充分策略，我们这里只是**下界**。
    **代码缺口**：blob 只能追加（`blob_append_grow`），回退要换掉尾部几行 ⇒ 需要"截断"原语；
    不必新造 —— 预算那套「整条丢弃」（`agent.c:2251-2271`）已是**"截断到记录边界"的只读版本**，
    而截断必须对齐段边界（又一次落到 A4 自定界）。
45. **`rewind` 是第三个 kind，不是能力；且它必须是首块**（2026-10-23，v1.14.18）。
    用户判断"这可能是第一个有别于这些 agent 的核心优化"。三条：
    ① **控制流不是能力**，判据是四条谓词 —— 会被拒绝吗 / 会失败吗 / 有输出吗 / 占信任量纲吗。
    `rewind` 四条全否（越界是**准入**不是执行失败；它不产出、不碰世界）
    ⇒ 套不上 `CapDef` 也不需要套 ⇒ **不占 `CAP_MAX` 那剩下的 5 个实现槽**。
    决定性论据：**CALL 与 DONE 本来就是控制流**（派发 / 终止），REWIND 只是同一枚举族的第三项
    —— 这不是往线格式塞新东西，是补齐一个本来就该有三项的枚举。

    是同一遍扫描里的两条结构断言。
    **截断点不必记** —— 回执三行永远在 blob 尾部 ⇒ 截断点 = 删掉尾部所有非 `#call`/`#result`

    ③ **收益是两笔账，我上一轮算错了**：**prefill 次数从 N 降到 2**

    **这笔与"第几段失败"（k）无关**，只要 N ≥ 3 就净赚；可回退那笔（不重复副作用 + 不重写已对段）

    ⇒ 修正上一轮的悲观结论（"k 集中在开头时可能贵 2~3 倍"）：**贵的是输出 token，而它很少**；

46. **段化分档的轴不是参数量，是"守格式率 p"；且损失是 `p^N` 超线性**（2026-10-23，v1.14.20）。
    用户提出"本地模型过小，和 27B 不是一回事，要不要分档"。**要分档，但别按参数分。**
    三件被"大小"混在一起的事，处置完全不同：
    **窗口**（限 N，纯算术）/ **守格式率 p**（限 N，且 `p^N`）/ **前缀正确率 k**（**只限回退，不影响 N**）
    ⇒ `N_max = min(窗口, 格式)`；回退开关由 k 定。
    **算术是这条线的核心**：`intent_ok` 是**原子**的（全合法才派，`agent.c:1473`）
    ⇒ N=4 时 `p=0.95 → 81%`、`p=0.80 → 41%` ⇒ 小模型不是"收益低"，是**段化根本起不来**
    （死在派发之前，连 `#fail` 都不产生，`stat_failed` 里看不出是哪一类）。
    **反直觉推论**：p 接近 1 之后，模型再大也不改善段化 —— 瓶颈从"能不能产出多段"
    转到"前缀对不对"，后者取决于任务难度而非参数量 ⇒ **27B 与更大可能没有可测差别**，
    断崖在"守得住/守不住格式"之间（≈本地 ≤8B / 量化后那档）。⚠️ 是假设，可测且不需任务成功。
    **量化的伤害路径具体**：最伤长输出一致性 ⇒ **尾段漂移** ⇒ 量化模型该用 `N=2` 不是 `N=4`；
    可测形式：同模型跑 N=2 / N=4 比 `stat_fail_seq` 的形状（集中后半 = 漂移；形状一致 = 整体难）。
    **一个当下的张力**：原子性对小模型**有害**（"3 对 1 坏"→"4 全不派"）。
    A（降到 N=2，零代码）先做；B（部分应用 + `#dropped` 收据）只在 `p̂∈[0.7,0.9]` 时做；
    **C（运行时替模型切分）永不** —— 同族于「运行时不能进归因」。
    **三个旋钮**（`N_max` / `atomic_batch` / `rewind`）**默认位必须等于现状** ——
    否则引入段化会悄悄改掉既有部署；且应由测量的 `p̂` / `k̂` **算出来**，不是被人调出来。
    **测量顺序不能反：p → N → k**（p 低则产生不了批次，测 k 是测空集合）
    ⇒ 下一刀的仪器是 `stat_batch_rejected` / `stat_batch_ok`（`agent.c:1473` 那一个分支），
    **不是** `#notrun` / `rewind`：它便宜、有 endpoint 就能测、且不需要任务成功。
47. **观测量与语义要分开处置：错误码可以归并，读数不能归并**（2026-10-23，v1.14.21）。
    这一条是第 46 条那句"下一刀的仪器"落地时**跑出来的**，不是想出来的 —— 三处新判据：
    **① `E[N]-E[k]` 不是 `E[N-k]`。** 它除的两个分母不同（`E[N]` 除全部批次，
    `E[k]` 除**有失败的**批次），且方向恰好反：失败率越低这个差越大，"只失败一次"
    会看起来像"能省很多段"。`agentctl` 与探针**都**印过这个数（两处都犯过错）。
    修法：**逐批配对**；一个进程里只有一批时相减才是精确值 ⇒ `agentctl` 在 `nN==1`
    印精确 `N-k`，多批时明说"这里算不了"并把配对交给探针（探针把"N 不唯一"的 run 单列）。

    不把重试策略塞进协议层（`agent_llm.h` 文件头的边界）；抹掉状态码则是把唯一能区分
    "凭据错 / 被限速 / 对端抖动"的事实扔了 —— 而这三者下一步动作完全相反，错判的代价是
    **"以为模型不肯分片"**。⇒ `AgentLlmCfg` 加 `last_status` / `last_rc` 两个**观测量**
    （在判 2xx **之前**写下），`chat_impl` 拆成"执行层 + 唯一写回点"（否则加第 7 条 return
    时必漏），**签名去掉 `const` 是刻意的**（留着再强转会让人以为它无副作用）。
    判据：**码合成一个，事实不能不留** —— 同族于"A5 混资源"与"低报的计数器比没有更坏"。
    **实测五档各自打对**：`http 0/io` · `401` · `429` · `503` · `200+format`；
    探针四条分支靠四个 `--scenario`（fail-last / fail-first / ok / idle）点亮 ——
    **一条剧本只点亮一条分支，没跑到的分支等于没写**（M10 全绿是因为从没被跑到）。
48. **测"愿不愿意分段"时，题目里不能出现段数**（2026-10-23，v1.14.22，第一次真实读数）。
    上一轮所有 `N=2` 都来自我题目里那句"**一次给出两个查询**"。同一批模型换成
    "尽量一次查完"/"这几个都查出来"之后给出 **1 / 4 / 6** ⇒ 那个 2 量的是我的指令。
    **读到 N 之前先读题目。** 同族于"判据必须可复现"：题目里写死了答案，读数就只是回声。
    同时被真实端点证伪的四处诊断，错误是同一个：**把 status 当判据**。
    `0+FULL`（请求体超 `REQ_CAP`）/ `200+RANGE`（段数超 `FANOUT_MAX`，不是模型不守格式）/
    `200+OK`（那条是成功的） / `404`（模型名不在分组，不是路径错；路径错的典型是 `200+HTML`）。
    ⇒ 判据 = **(status, rc) 二元组**：`rc` 是我们的结论，`status` 只是对端的态度。

    内部就返回 `RANGE`，**不经过 `intent_ok`** ⇒ 三个计数器一个没动 ⇒ 印"没有任何产出尝试"。
    模型明明产出过、被我们拒了，读数却说它没尝试 —— 丢掉的恰好是"要不要抬上限"的唯一证据。
    **两个上限已成真实瓶颈**：`REQ_CAP` 16KB（4 段 grep 结果回填即爆）、`FANOUT_MAX` 8（9 段被拒）。
    附纠正：`AGENT_ACT_BATCH=4` 是**每 tick 执行容量**，实测 n=6 正常派发（分两 tick）；
    批的解码上限是 `AGENT_FANOUT_MAX=8`，两个数此前一直混着说。
    ★ **k 仍无样本，且不是采样不足**：只读族（幂等、参数宽松、**零命中合法**）几乎不产生
    可定位的执行失败 —— 让模型读不存在的文件，它改用 `fs.grep`，而 0 命中是合法结果
    （`executed 4 failed 0`，两 rep 复现）⇒ **在只读族上谈"回退省几段"是拿空集合算期望**；
    k 要有读者，前提是先有写族那种"会失败且失败有位置"的能力。
49. **失败短路的代价不在"多跑一段"，在"决策被推给模型"**（2026-10-23，v1.14.23，写族实测）。
    上一轮说"k 要有读者，前提是先有写族"——**同一天被兑现**：把 `fs.write_apply` 打到不存在的
    父目录，`k` 立刻有了三个样本（`k=1 / 1 / 2`，单批那次 `N-k = 1` 精确）。
    但比 `k` 本身更值钱的是**同一批收据里的两行并存**：`#fail 1`（seq 1）与 `#result`（seq 2）
    ⇒ 第 1 段失败后第 2 段照常执行，且落盘字节可核对（`a.c` 确实被改成 43）。
    ⇒ 今天模型拿到的事实是"两件事都做了、一件失败"，**"哪件其实没做成"要它自己推**。
    run C 的轨迹把这笔账记下来了：为搞清 `nodir/z.c` 为什么失败，它花了 **3 次调用**
    （`fs.grep` → `fs.grep .` → `fs.diff`），而"父目录不存在"**运行时那一刻就知道**。
    ⇒ `err`（`WI_FAILED` 带错误类别）的价值第一次有量级：**省 3 次调用**，不是"少一句话"。
    边界不提：完整归因仍归模型（§4.18.15：位置归运行时、归因归模型），
    但"父目录不存在"属于**运行时已持有的既有事实**，不是语义判断。
    **推论一（`k` 的可信性来自字段不是顺序）**：`#fail <seq> <cap>` 的 `seq` 是派发时写进
    `WorkItem` 的座位号，与回填文本里排第几无关（三种顺序都真实存在，`agent_types.h:51`）。
    ⇒ 若哪天 `k` 变成"数到第几个 `#call`"，这份读数立刻作废。
    **推论二（`p̂` 高不等于给得宽）**：同一句任务三次跑出 `N=2 / 2 / E[N]=1.25`。
    `p̂` 只说明"给的都合法"，不说明"肯一次给几段"。⇒ 分档定 `N` 必须 reps；
    "读数之前先读题目"再下一层：**读完题目还要问"这个数在重跑下变不变"**。
50. **观测字段的价值要分"被读到"与"改变行为"两件事记**（2026-10-23，v1.14.24，`err` 落码）。
    `#fail <seq> <cap> <why>` 上线后，模型确实读了新字段 —— 收尾措辞从"写入失败（`#fail 1`）"
    变成"写入失败（**IO 错误**）"。但**它仍然 `fs.grep` + `fs.diff` 各探一次**，
    只比上一跑少 1 次调用（4 vs 5）⇒ **我上一轮预测的"省 3 次调用"被这一跑证伪**。
    根因不是字段没写对，是**粒度不对**：`io` 说的是"哪一侧出错"，
    而模型要的是"为什么"（父目录不存在）—— 后者只有实现知道（errno）。
    ⇒ 判据①：**"读数进了上下文"与"读数改变了下一步"是两件事，必须分开报**；
    只报前者会把一个观测升级说成一次收益。
    ⇒ 判据②：观测的粒度停在**运行时能确定的那一侧**是对的（归因归模型，§4.18.15 同源）。
    想把"为什么"也给出去，就得动 `CapImpl.exec` 的签名 —— **先不建**：
    收益是 1 次调用/失败，代价是 12 个实现改 ABI。触发条件：探查类调用
    （`grep`/`diff`/`ls` 指向同一路径）占失败次数的比例持续 > 1。
    ★ **上面这条"只能动 ABI"当场被自己查代码推翻**（同日，追问"LLM 会不会问为什么、加剧用量"时）：
    信息链是 `errno → rc → why → 模型`，而 `agent_fs.c` 里**每一个** `open/lstat/realpath`
    失败都 `return CXF_ERR_IO` —— 15 个 errno 在**第一跳**就塌成一个码。
    ⇒ 我在第三跳加六个词，**漏斗在下游没有任何意义**。判据③（新）：
    **"下游加词"之前先看"上游有没有把信息扔掉"** —— 观测宽度的瓶颈通常在漏斗，不在管道末端。
    便宜的那条路在实现里：`ENOENT` 单独映射成 `CXF_ERR_DEP`（一个 `errno` 分支、零新增结构），
    先当**实验代理**跑 2~3 reps，看模型是否少探一次；它证明了"给事实有用"，再讨论
    要不要新增 `CXF_ERR_NOENT` 让它转正。
    结构侧三条（都进代码）：① `WorkItem.err` **追加在末尾**——第一版放在 `status` 旁边，
    被 `test_types` 的"既有列号不变"契约挡下（语义要同表、布局要追加，两者不冲突）；
    ② 写入口从 6 处收敛成 `item_fail()`，因为 `status`/`err`/`stat_failed` 是同一件事的
    三个投影，"同住一个结构"要推进到"同一个入口"；
    ③ `err_word` 未知值返回 NULL 让调用方印 `e<num>`，`CXF_OK` 印 `?` ——
    兜底成 `"?"` 会让"枚举加了值、表没跟上"变成一句**正常**回执。
    ★ 新断言的最有价值一条是**反断言**（`!fs_has(… "#fail 2 fs.grep ?")`）：
    正向断言只证明"对的那条写对了"，反断言才抓"别处漏设"（M2 变异红 2 处，其中一处就是它）。
51. **工具面的开销不在"放哪"，在"改的时机"**（2026-10-29，v1.14.25，两次实测）。
    用户的反驳把一条判据改对了：**改 `tools[]` 不是"KV 命中率归零"，是"一次全量 prefill"** ——
    改完新前缀照常被缓存。所以问题不是"能不能改"，是"这次改动值不值一次 prefill"。
    算术：prefix ≈ `tools 2803 B + system 91 B + 问题 209 B ≈ 3.3 KB`；一个工具 ≈ **250 B**
    （203 B 脚手架 + desc）⇒ 要把一次 prefill 赚回来，新增工具得在 **≈13 轮**里被用到。
    一次会话 4~8 轮 ⇒ **单会话内晋升几乎永不划算**；常驻集只能按**跨会话复用率**定。
    ★ **冷窗口（长空窗）只是必要条件**：它让"那一次 prefill"变便宜，不能让单会话内晋升变划算。
    ⇒ 推论一：**折叠的展开落在后缀，一次都不改 prefix**（`tools[]` 在 prefix 上，展开在 suffix 上）。
    ⇒ 推论二（实测）：`tools` 只声明 `fs.grep`、`fs.write_apply` 只写在正文里，模型**直接发出一个
    未声明的 `tool_call`**（args 连 `\n` 都对）⇒ 折叠可行；但这条依赖**对端不校验 name**
    （严格实现会 400），属于买来的契约 ⇒ 只能当证据，落码必须**明示 `CALL|` 语法**。
    ⇒ 推论三：**"运行时自增长"只剩两层 —— 组合（配方）与折叠（说明）**。"写新能力"要编译，
    且 `resolve_in_root`/`path_shape_ok`/`within` 全是 `static`（新文件用不上，只能复制，
    而**安全边界最不该有两份**）⇒ 那一层是**提案**（人/CI 合入），不是热加载。
    ⇒ 推论四（劝退数据）：让它写 80 行 C 的 `CapImpl.exec`，三次尝试 = 180 s 超时 / 连接被拦 /
    **21 分钟未返回**（人工中止）⇒ 长输出在这条中转链路上**取不回来**。要下"模型写不出"的结论，
    得先换一条能返回长输出的通道。

部署矩阵现在是 6 档（前 5 个是 fs，第 6 个与它们**正交**）：`--root`（只看）/ `--diff`（能看差异）/
`--create`（能建不能改）/ `--write`（能改，含 diff）/ `--append`（能追）/ `--net HOST:PORT`（能出网）。
实测工具卡 1872 / 2360 / 2360 / 2848 / 2803 / 2392 / 2880 / 3323 / 3368 B（单能力 ≈ 488~520 B），
加 `--net` 后 2312 / 2832 / 3763 / 3808 B。**每一档都是"加一个描述符"，没有一档是"改一个开关"。**

**第五刀改了上一段的结论一次，不是补了一刀：`http.post` 本来是"`CapRerun` 的第一个真读者"，
落下来它却主动拒绝了 `FULL`** —— 所以 `CapRerun` 至今**仍是零读者**，那半块 A1 的处境
比上一版更糟，不是更好。

推演只有一步。框架的 `FULL` 语义是"再给一倍、把 `exec` 从头再调一次"（`agent.c:1829-1843`，
下面这段代码没变过）：

```c
/* tests/agent.c:1829-1843（节选） */
rc = CXF_ERR_FULL;
for (uint32_t a = 0; a < AGENT_RESULT_TRIES; a++) {
    rc = api->exec(api->ctx, args, args_len, out, res_cap, &out_len);  /* ← 从头再调一次 */
    if (rc != CXF_ERR_FULL) break;
    blob_reserve(s, res_h, res_cap * 2u); res_cap *= 2u;
}
```

对 fs 族"从头再调一次"是白写一次；对 `http.post` 是**再发一次 HTTP 请求** —— 对方收两次、
按次计费、可能已经产生了不可撤的副作用。"把它写对一点，让重跑安全"这条路不存在：
**世界已经动过了**。所以唯一正确的选择是**不让这次重跑发生**：响应超限 ⇒ `#truncated` + `CXF_OK`，
输出缓冲本身太小 ⇒ `RANGE`（把重跑许可收回去，宁可失败也不重发）。

| 能力 | 会 `FULL` 吗 | 重跑会二次生效吗 | 谁该负责 |
|---|---|---|---|
| `fs.write_new` / `fs.diff` / `fs.write_apply` | 不会 | 不会（幂等 / 纯函数） | 不需要 |
| `fs.append`（已落码） | 不会（收据定长） | **会**（内容多一份） | **能力契约**（尾部比较，§4.18.9） |
| `http.post`（已落码） | ~~会~~ → **主动不 `FULL`**（改报 `#truncated` / `RANGE`） | 会（对方收两次，且是钱） | **能力契约**（§4.18.10） |

⇒ **判据第三次收紧，这一次是往回缩**：不再是"谁会发起那次重跑"，而是
"**这次重跑该不该被允许存在**"。fs 族的"重复生效"来自模型的重复调用（框架看不见，靠能力契约挡）；
出网族的"重复生效"更彻底 —— **框架也不该有机会发起它** ⇒ 契约的目的不是"让重跑安全"，
是**让 `FULL` 这条路根本走不到**。
两句话合成一条：**能当场说清"我这次没做"的（fs 族）靠收据，说不清且世界已动过的（出网族）靠不让它重跑。**

**`CapRerun` 的处置（v1.14.6 已判死，这一段是当时的推理，留着当反例）**：
它当时的定位是"**为一个不存在的读者预留的字段**"。而 grep 给出的实情更干脆 ——
**零行代码**，连"预留"都只在注释里。⇒ **不删（没得删），也不建**：

| 实现 | 会 `FULL` 吗 | 重跑代价 |
|---|---|---|
| `fs.grep` / `fs.diff` | 会 | 0（只读 / 纯函数） |
