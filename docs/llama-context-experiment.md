# llama.cpp 上下文同步与 KV 调度实验

> 统一展示与跨阶段比较见 [测试成果汇总](benchmarks/README.zh-CN.md#e0102--直接-api-可行性)，本报告对应 E01–02；原始样本已归档至 `docs/evidence/`。

日期：2026-10-30。目的：验证 Agent 掌握的上下文变更信息能否直接驱动引擎，
并分别测量显式边界、共享前缀分支、提前预填充、状态保存恢复的收益与限制。

## 环境和范围

- 硬件：Apple M5，16 GiB 统一内存，macOS；29/29 层实际卸载到 Metal GPU。
- 模型：本机已有 `Qwen3-0.6B-Q8_0.gguf`，权重约 604 MiB；本轮没有下载新模型。
- 动态库：本机已有 llama.cpp b10938；另下载官方 b10938 源码，核对提交为
  `f1e44dcc11d8802d107bd7331a3d3fd3e6f57b93`，头文件和二进制一致。
- 直接调用 C API，一个 `llama_context`，`n_seq_max=2`、统一 KV 池、4 CPU 线程，
  `n_batch=n_ubatch=512`。KV 使用引擎默认 FP16，预分配缓冲 364 MiB。
- 固定文本生成 2048 token 前缀；六次追加，每次 128 token，最后 2816 token。
  fixture 原文 11088 B、token ID 11264 B。每个分块边界都先验证：分段分词结果与全文分词逐 token 一致。
- 每种模式先预热，再轮换测量顺序。主试验每组 5 样本，较慢输入每组 3 样本。
- **这不是整个 Agent 的基准**：不含 HTTP、聊天模板渲染、模型加载、初始公共前缀的计算、
  生成答案或任务完成率。流式输入是预先分好 token 的定时到达模拟，没有调用云端模型。
- 原始数据、样本范围、模型 SHA256、源码提交和编译／执行参数保留在实验目录。
  最终主试验还保存了 C 源码快照及其 SHA256。

## 1. 已有前缀缓存 vs 显式变更边界

六次追加的累计耗时，中位数：

| 路径 | 前端分词／物化／比较 | 引擎处理 token 数 | 累计耗时 |
|---|---:|---:|---:|
| 每轮从头计算 KV（上界对照） | 6.680 ms | 14976 | 3429.592 ms |
| 公共前缀缓存＋全文分词和扫描 | 6.378 ms | 768 | 296.696 ms |
| Agent 给定稳定边界＋只分词追加段 | 0.592 ms | 768 | 294.259 ms |

前端工作约下降 91%；总耗时中位数只下降约 0.8%。两者总耗时范围分别为
288.482–305.889 ms 与 290.348–302.362 ms，明显重叠，**不足以声称获得稳定的端到端加速**。
第一次探索运行的总耗时下降约 1.7%，也说明这一小收益需要控制波动。

单独比较 2688 个相同 token 的公共前缀，20000 次循环，每次约 **0.649 微秒**。
因此本尺度下主要消掉的是全文重新分词，前缀比较本身不是推理瓶颈。
全文路径每组重新分词 14976 token，增量路径只分词 768 token。

与不缓存的 3.43 s 相比，已有缓存本来就能缩到约 0.30 s。
**这部分收益属于 llama.cpp 已有 KV 复用，不能记成 cxf 新增收益。**

本轮不证明删掉重复原文能省大量内存：原文和 token 序列各约 11 KiB，
而下面仅 2048 token 的引擎序列状态就约 224 MiB。普通 Agent 也不一定自己另存一份 KV。

## 2. 流式到达时提前预填充

在已经计算好的 2048 token 前缀上追加 512 token。
每次输入源到达 32 token；比较等全部到齐、每块立刻计算、合并到至少 128 token 再计算。
合并策略也会一次处理已经到达的积压块。

较快模拟输入：每 20 ms 到达 32 token，相当于 1600 token/s，输入阶段共 320 ms：

| 策略 | 本地引擎执行耗时 | 输入结束后的等待 | 从输入开始算的总耗时 |
|---|---:|---:|---:|
| 等全部到齐，批量 prefill | 162.959 ms | 168.441 ms | 488.441 ms |
| 每 32 token 立刻计算 | 379.173 ms | 84.184 ms | 404.184 ms |
| 至少 128 token 合并计算 | 188.634 ms | 51.571 ms | 371.571 ms |

合并策略总耗时降低约 23.9%，尾部等待降低约 69.4%。
但这是假设的快速输入速率，不是实测云端吞吐。

较慢模拟输入：每 200 ms 到达 32 token，相当于 160 token/s，输入阶段共 3200 ms：

| 策略 | 本地引擎执行耗时 | 输入结束后的等待 | 总耗时 |
|---|---:|---:|---:|
| 等全部到齐 | 181.603 ms | 186.644 ms | 3386.644 ms |
| 每 32 token 立刻计算 | 382.355 ms | 28.731 ms | 3228.731 ms |
| 至少 128 token 合并计算 | 193.884 ms | 58.624 ms | 3258.624 ms |

这一组立刻计算的尾部等待下降约 85%，总耗时只下降约 4.7%；合并策略总耗时下降约 3.8%。
输入越慢，额外计算越容易被等待隐藏，但整体耗时也越受输入源限制。

**反例控制**：所有 512 token 一开始就已可用时，批量计算约 171.190 ms，
强制拆成 32 token 小块约 383.562 ms，反而慢约 2.24 倍。
收益来自重叠等待，不能把小块的多次前向执行当作免费，也不能把执行耗时增长误报成 FLOP 增长。

## 3. 子任务复用同模型的前缀

在同一个统一 KV 池里，用 `llama_memory_seq_cp` 把序列 0 的 2048 token 前缀关联到序列 1：

- 前缀分支操作：中位数 **0.058 ms**；重新计算同样前缀：**435.960 ms**。
- 分支后再计算 128 token：共 **48.053 ms**；从头计算前缀再追加：共 **482.189 ms**。
- 公共前缀的首次计算在两边都不计时，它已经由父任务完成。

固定版本源码 `src/llama-kv-cache.cpp` 的 `seq_cp` 在同一 stream 内仅更新 cell 元数据，
不复制 KV 数据。本试验统一池满足这个条件。
这说明 Agent 已知子任务共用前缀时，可以直接利用引擎现有能力，避免重建子任务状态。
**不适用于不同模型之间直接共享 KV，也不证明跨独立 context 的复制免费。**

## 4. 保存恢复可用；删序列不等于归还物理内存

2048 token 序列的序列化状态为 **234906296 B（224.024 MiB）**：

- 导出到 CPU 缓冲：中位数 **10.194 ms**，范围 4.742–16.449 ms。
- 恢复：中位数 **5.573 ms**，范围 4.460–9.722 ms。
- 删除序列的元数据约 0.1 ms；五个样本删除前后的进程 resident size 均相同。
- 删除前后都保留着预分配的 364 MiB KV buffer；保存状态还需要额外 CPU 缓冲。

因此当前接口足以做逻辑挂起／恢复、复用空闲 cell，但**本实验没有实现 GPU 显存卸载回收**。
要把这变成真正归还显存的策略，需要进一步研究 buffer 生命周期或分页／池的内存管理。
Apple 统一内存下的复制耗时也不能代替 Windows 独显上的 PCIe 搬运测量。
这里记录的是进程当前 resident size，不是独立 GPU VRAM 计数器。

## 正确性与边界

- 显式增量与缓存路径逐项比较最终词表 logits，本次观测最大差为 0，top-1 一致。
- 流式不同分块、共享分支和保存恢复的 logits 比较，本次也均一致。
- 修改位置 2048 的一个 token，logits 最大变化 15.410506；从该边界撤销 KV 再重算，
  与从头计算修改后的序列差为 0。这个正向控制避免把过期 logits 或空跑误当成正确。
- 结果只对应本机、这个小模型、稳定分块和本批次设置。一般聊天模板、BPE 未提交尾部、
  多模型调度、多租户、实际云端流、长上下文与 Windows GPU 均未在本轮验收。

## 复现与证据

```sh
# 头文件必须与动态库版本一致；本机已有对应动态库和模型。
git clone --depth 1 --branch b10938 https://github.com/ggml-org/llama.cpp.git build/llama.cpp-b10938
python3 tools/bench_llama_context.py --repeats 5 --prefix-lines 128 --out build/new-context-trial
python3 tools/bench_llama_context.py --repeats 3 --stream-gap-ms 200 --stream-only --out build/new-slow-stream-trial
```

已有源码时无需重复 clone。其他机器用 `--sdk`、`--runtime`、`--model` 指定匹配的路径。
运行器当前支持 macOS/Linux；原生 Windows 的构建／计时部分尚未移植。

- 最终主数据：`build/llama-context-final-20261030/{manifest.json,raw.jsonl,raw.csv,summary.json,engine.log,bench_source.c}`。
- 较慢输入：`build/llama-context-slow-stream-20261030/`。
- 探索数据：`build/llama-context-baseline-20261030/`、`build/llama-context-smoke.jsonl`。
- 实验代码：`tests/bench_llama_context.c`；构建与汇总：`tools/bench_llama_context.py`。
