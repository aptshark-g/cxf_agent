# 并发状态访问对照实验：复制输入与共享不可变版本（草案）

> 证据分类见 [成果汇总](benchmarks/README.zh-CN.md#l01--早期观测仅文档读数)。本方案未运行，不能引用为实测性能成果。

> 状态：设计／实验草案，2026-10-17。
> 本文提出的快照、依赖版本校验、提交协议与旧版本回收均未实现；没有运行本实验，没有性能证据。
> 范围：cxf 内核之上的最小并发状态实验；不要求完整 Agent 框架，不改变现有内核接口。
> 判断：先把两组的有效性语义做成同一件事，再比较成本。只有共享不可变版本在目标负载下取得可重复的有效收益，且资源预算可接受，才考虑采用。

## 1. 现状与问题

cxf 当前用显式所有权和生命周期管理存储：

- 跨模块引用约定使用 `cxf_handle { index, gen }`。handle 不拥有目标，不计对象引用，不保证目标存活；解引用由原表验证世代。
- table／SoA 的行由所有者显式 remove／clear／release。remove 回收槽位并使旧 handle 失效，不递归处理字段引用；release 释放表自身的列与索引，不释放裸指针指向的独立资源。
- frame arena 在帧结束回退水位，chunk 留待复用；state arena 的模块状态保持到 world release。模块自建资源由 deinit 释放。
- 内核没有根集合、对象图可达性扫描、mark-sweep 或 cycle collector。若 A、B 是表中互相持有 handle 的两行，外部引用消失不会自动删除两行。
- 模块 HARD 依赖的拒环与 refcount 服务于装配和卸载保护，不是对象引用环的垃圾回收。

依据：[`handle.h`](../include/cxf/handle.h)、[`table.c`](../src/table.c)、[`soa.c`](../src/soa.c)、[`arena.c`](../src/arena.c)、[`world.c`](../src/world.c)。设计背景见 [注册期](registry.md)、[类型树与 SoA 自动布局](type-layout.md)。

本次问题是：耗时计算需要并行时，怎样读到一致输入、判定结果是否仍可提交，以及何时安全释放被替换的旧数据。不可变版本是候选存储方案；它本身不会判断结果是否过期，也不会自动回收任意对象引用环。

## 2. 先定数据和所有权

以下是拟议的实验概念，不是已有 cxf 类型或 API。

| 概念 | 至少记录什么 | 所有权与职责 |
|---|---|---|
| StateOwner | 当前已发布视图、提交序号、对象／键版本 | 单管理者串行处理状态获取、外部更新、校验与提交 |
| PublishedView | 视图标识、只读数据、对应版本信息 | A 导出一致的私有副本；B 提供受保护的不可变版本 |
| TaskInput | task_id、attempt_id、输入视图、读依赖、写入基准 | worker 只消费本次尝试的稳定输入 |
| Proposal | 计算结果、完整读依赖、拟写集合及其基准版本 | worker 产出提案，不能自行发布共享状态 |
| VersionLease | 被保护版本、持有者、有效状态 | B 在安全获取时建立保护，终态／取消时归还 |
| RetiredVersion | 已脱离当前根的版本、仍存活的使用者／保护记录 | 只有所有读取者和借用者均退出后才允许回收 |

版本语义必须拆开：

- `handle.gen` 识别槽位删除／复用，不等于数据内容修订号；对象原位改变时，现有 generation 不会自动更新。
- 内容 revision 用于依赖有效性判定；每次相关逻辑写入都要更新，删除也要有可检查的版本／墓碑。
- snapshot_id 标识一个一致的已发布视图；单独比较快照号可能把无关更新也判为冲突。
- tick_count 不能直接代替上述版本语义。依赖键也不能只有 handle 数值：handle 只在所属表／所有者中有意义。

首切片使用固定键空间和有限定长数据，避免先引入通用对象图和隐式所有权。动态查询、范围查询、缺失项读取若后续加入，必须把相应谓词／集合版本和“不存在”也记为依赖，否则会漏检新增对象等变化。

## 3. 两组共同的正确性契约

在运行前冻结以下语义，并对 A、B 同时执行：

1. 每次尝试读取一个一致视图；不允许把不同时刻的字段拼成从未存在过的状态。
2. worker 不可变更共享状态，所有结果均以 Proposal 提交。
3. 默认采用严格依赖有效性：提交时，所有读依赖和必要的写入基准仍满足本次任务的契约；相关更新使校验失败。无关更新是否拒绝由同一校验粒度决定。
4. 校验与结果发布／状态写入是管理者内的一个不可分割动作；任何更新不得插入“校验成功”与“提交生效”之间。
5. 校验失败时，两组使用相同的重试、退避、最大尝试次数、截止时间和取消规则。已作废的计算不计为有效完成。
6. 相同 task_id 的重复提案不得重复发布；attempt_id 区分每次尝试，旧尝试迟到不得覆盖新结果。
7. 输入、配置、规则或其他会影响正确性的依赖必须纳入实验模型。首切片直接记录实际读取的键；不把模型猜测的依赖当作完整依赖集。

“允许旧快照”是另一种可选契约，不能只给 B 使用。若允许按读取时刻回答、允许有界陈旧或允许特定不变式下提交，应在实验前给出精确定义、版本／时间界限和 oracle 判据，并对两组同时启用。保留旧输入的内存安全，与允许旧结果提交的业务语义，是两个独立条件。

严格校验不能仅比较拟写对象：即使只写 C，若结果依赖的 A 已变化，也必须处理；多个对象的不变式、盲写的写写冲突也要按共同契约验证。

## 4. 对照 A：并行计算＋单管理者＋私有输入副本

A 的共享状态读写和提交串行，耗时计算并行。它不是“拿着全局锁完成整个耗时任务”。

### 4.1 数据获取

1. worker／任务入口向管理者请求一份输入。
2. 管理者在同一个串行步骤中读取所需数据，复制成 worker 私有输入，并同时记录匹配的依赖版本与写入基准。
3. 复制完成后释放管理者执行权。私有副本在这次尝试结束前保持稳定，worker 不再追读可变共享对象。
4. 若读集合预先未知，首切片统一复制预先声明的输入范围，计算时记录实际读取集合；A、B 使用相同输入范围和实际读依赖规则。不能让 B 拿到更少数据却把差异归于并发模型。

大副本的复制可能占用管理者较长时间，这个成本要计入队列等待、获取耗时和 CPU。若改用分块复制，必须提供一致性协议；不能在没有证明的情况下让更新穿插复制过程。

### 4.2 计算

worker 在私有副本上并行执行确定性耗时任务，产出 Proposal。管理者可继续处理其他获取请求、外部更新和提交。计算全程不持有共享状态锁或管理者独占权。

### 4.3 提交与失效

管理者在一次串行提交步骤内验证读依赖和写入基准：

- 通过：一次性发布结果／写入，更新相应 revision 和提交序号。
- 冲突：不产生可见写入；结束本次尝试，按共同策略重新获取输入并重算。
- 超时／取消／预算耗尽：进入明确终态，清理副本与提案；不能把失败计作完成。
- 即使耗时任务已全部算完，只要契约要求的依赖已失效，仍必须拒绝该结果。

因此，在严格有效性契约下，A 同样可能使用乐观并发控制式的“先算、提交前校验”。“单管理者”并不自动保证锁外计算的结果仍然有效。

## 5. 对照 B：并行计算＋共享不可变版本＋受保护读取

B 仍可使用同一个单管理者串行提交；不把多写者提交作为本轮附加变量。

### 5.1 安全获取与计算

1. 获取一个一致的已发布不可变视图，并在同一安全协议中建立 VersionLease。
2. worker 在保护有效期间直接读取共享版本，记录与 A 相同定义的读依赖，产出 Proposal。
3. 更新创建新数据／新版本并发布，不原位改写已交给 reader 的内容。
4. 版本发布的一致性单位必须覆盖任务所需的多键状态。仅把若干指针各自改成 atomic，不足以证明读到一致视图。

首切片可考虑由管理者串行完成“读取当前视图＋登记 lease”，归还 lease 也经管理者处理。这样计算阶段仍可并行，且能明确关闭获取与保护的竞争窗口。是否最终采用这个方案，或 epoch／hazard 等机制，尚待设计；不能先按无保护裸指针实现再补说明。

### 5.2 校验、提交与回收

B 在与 A 相同的提交入口验证相同依赖；通过才发布。持有旧快照只保证可安全读取，不豁免版本校验。冲突后必须释放旧尝试的资源，再按共同规则重试。

旧版本脱离当前根后先进入 retired 状态。只有当前根不再引用它，且 reader、提案、异步借用者等全部退出，才可释放版本拥有的存储。超时、取消、worker 退出和长期不归还 lease 都要有明确处理；不能为压低峰值内存而提前回收。

版本内对象可互相引用，但回收单位和所有者必须显式：如果整个版本／区域共同结束，可以整体释放而无需遍历环。若跨版本／共享块继续被引用，必须另有所有权和保护协议；不能假定任意图引用计数会收掉孤立环。首切片不引入隐式跨版本裸指针，结构共享及其元数据回收机制待定。

## 6. 真正的实验变量

主要对照固定同一个管理者、提交协议和依赖粒度：

| 项目 | A | B |
|---|---|---|
| 耗时计算 | 并行，稳定私有副本 | 并行，受保护的共享不可变版本 |
| 获取状态 | 管理者一致复制并记录版本 | 安全获取一致版本并建立保护 |
| 提交 | 串行校验＋发布 | 相同的串行校验＋发布 |
| 相关更新后的旧提案 | 按共同契约拒绝／重试 | 按同一契约拒绝／重试 |
| 核心成本差异 | 复制字节、私有副本占用 | 保护开销、版本创建与旧版本保留 |

首轮真正自变量是“复制稳定输入”与“共享受保护的不可变版本”。两组都需要校验时，不能把 A 写成没有校验，把 B 的收益归因于独有的校验能力。

若研究校验粒度，另设正交矩阵：A-粗／A-细／B-粗／B-细。粗粒度可用整个输入范围／全局 epoch，细粒度可用实际依赖键 revision。分别报告复制方式和粒度带来的作用；“B 细校验赢 A 粗校验”只能证明组合方案差异，不能单独证明不可变存储更优。

OCC（乐观校验）、MVCC（多版本共存）、依赖追踪是已有成熟机制的来源。本文借鉴其机制形状，不声称 cxf 已有这些机制，也不因用了这些名字就获得某个数据库隔离级别。本项目仍需具体定义数据结构、验证边界、发布顺序与回收协议。

## 7. 最小实验负载

先做独立的小型状态／任务驱动，不搭完整 Agent：

- 固定键值或小型记录状态；任务读取若干键，做可控的确定性计算，提出结果或状态更新。
- 明确 task_id、输入范围、实际读集合、拟写集合、更新事件、取消事件与预算。
- 用纯 CPU 工作量控制计算时长；如另测等待型任务，单列该负载，不能用 sleep 结果代替 CPU 计算结论。
- 外部更新生成器与任务生成器使用保存的种子和事件序列。先注入可控制的交错，验证失败路径，再测真实并发性能。
- 用确定性 oracle 检查视图一致性、读写依赖、允许陈旧规则和每次已接受提交。oracle 按实际串行提交日志判合法性，不要求两个合法调度产生逐字相同的最终状态。

改变以下负载轴，同时保留低冲突对照：

| 轴 | 要观察的变化 |
|---|---|
| 任务时长 | 校验前相关数据变化的机会、废弃计算量 |
| worker 并发数 | 管理者队列、CPU 饱和和保护元数据开销 |
| 外部更新率 | 冲突率、重试与旧版本产生速度 |
| 读写重叠 | 任务读集与更新／写集重叠；热点与无关更新分别测 |
| 数据量／输入范围 | A 的复制成本、B 的保留与创建成本 |
| 读取者停顿／取消 | lease 归还、旧版本积压及回收安全 |

取值范围、读写分布、目标负载、版本粒度均待确认；不先编造代表性参数或收益百分比。

## 8. 公平运行与记录

1. 两组使用相同初始状态、任务及外部更新事件、worker／CPU／内存预算、运行窗口、最大尝试次数和截止时间。
2. 外部更新按相同计划时间／逻辑序号注入，不以某组已完成任务数来调节注入。记录计划与实际应用时间、队列延迟、积压和排空成本。
3. 正确性交错由可重复调度控制；性能运行保留同种子配对并记录实际事件顺序。不能把顺序不同的结果未经 oracle 判断就叫错误。
4. 获取、复制／pin、计算、校验、提交、冲突、退避、重新获取、取消与回收都纳入计量。不得把 A 的复制排除在计时外，或把 B 的旧版本内存排除在预算外。
5. 预热规则、构建选项、机器、核数、亲和性、输入序列和随机种子记入结果。A/B 顺序随机或交替，多次配对重复，报告离散程度／不确定性及异常运行，不只选最好一次。
6. 同一原始任务的多次尝试算一个任务。被拒绝、超时、取消或耗尽预算的任务分别报告，不能通过丢弃慢任务美化延迟。
7. 若请求量超过服务能力，报告有效吞吐、积压、更新应用延迟和排空时间；不得只取稳定小窗口掩盖管理者拥塞。
8. 两组使用相同的测量工具与采样方式；记录测量本身的开销。没有测得的字段标为未测，不补估计值冒充证据。

## 9. 指标与正确性门禁

### 9.1 性能和资源指标

- 有效吞吐：单位时间内通过 oracle、只生效一次的原始任务数；另报提交、拒绝与终态失败数。
- 端到端耗时：从原始任务进入系统到最终完成，包含获取、队列、全部重试和退避；报告 p50、p95、p99 及尾部样本量。
- 同时报告成功任务与所有终态任务的延迟、超时／失败比例，避免只看幸存任务。
- CPU 时间／利用率、worker 和管理者占用、上下文切换（如可测）。
- 峰值内存：当前数据、A 的私有副本、B 的旧版本、共享块、lease、提案、队列和回收元数据；分别报告 allocator 账目与进程实际内存口径。
- 校验与提交成本：检查依赖数、耗时、队列等待、复制字节、版本创建与保护／回收成本。
- 冲突、拒绝、尝试次数、废弃计算的 CPU／时间占比，以及因粗粒度造成的无关更新拒绝。
- 饥饿：每任务重试分布、最长等待、预算耗尽、长期无法完成的任务和长期持有旧版本的 reader。

### 9.2 必须先过的正确性门禁

| 门禁 | 可控反例／应满足的行为 |
|---|---|
| 一致视图 | 在多字段更新中插入读取；不得观察到半个版本 |
| 错误提交 | 读取后修改相关依赖、删除或复用槽位；旧提案按契约拒绝 |
| 依赖完整 | 修改实际读取但未写入的键；仍需检测；无关更新按共同粒度处理 |
| 校验到提交窗口 | 在两者之间安排更新；必须被同一提交动作排除或重新校验 |
| 快照获取到保护窗口 | reader 取版本时同时替换并尝试回收；不得先释放后 pin |
| 提前回收 | 暂停 reader、延迟提案、触发取消与恢复；任何仍可能访问的版本不得释放 |
| 重复提交／迟到尝试 | 重送同一 Proposal、让旧尝试晚到；不重复生效、不覆盖较新终态 |
| 重复外部副作用 | 重试同一逻辑任务；只允许共同协议定义的效果，不重复支付／写外部系统 |
| 清理与饥饿 | 冲突、取消、失败后保护与副本有退出路径；不静默泄漏或无限重试 |

任一门禁失败，该实现的性能结果不得用作采用依据。故障注入先使用模拟状态和模拟副作用，不连接真实支付、消息发送或其他不可逆系统。

## 10. 外部副作用不是“结果可撤销”

先算后验适用于可丢弃的计算与尚未发布的提案，不能据此撤销已经发生的外部效果。

首切片的 worker 只计算，不产生外部副作用。后续若接真实工具，两组必须共用明确的副作用协议：提交前仅暂存意图；需要时使用持久化意图、task_id 幂等键、重复检测和外部系统的确认／恢复机制。内存内串行提交本身不能证明跨进程崩溃后的 exactly-once。

补偿操作也不等于原操作未发生，不能把“以后可补偿”当成允许无校验重复执行的理由。无法满足共同协议的工具先排除，不让 A/B 获得不同的有效性保证。

## 11. 推进顺序与采用判据

1. 冻结共同有效性／陈旧语义、目标负载、预算和依赖定义。
2. 定数据结构、提交原子边界、B 的获取保护与旧版本回收协议。
