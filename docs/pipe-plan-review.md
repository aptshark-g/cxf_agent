## 0. 一句话

提案选对了位置（fan-out 与逐步 CALL 之间的空档确实存在），也提出了一个可复用的判据
（§1 步间衔接必须是数据性的）。但 **P1 用"接口类型相等"去校验一个"字节级全量替换"，
层面选错了** —— 按现有类型图，管道一条合法链都组不出来；而它举的两个例子
（`fs.read`、三步读写）一个能力不存在、一个在类型上不可能。

## 1. 站得住、应当保留的三样

1. **§1 那条判据**（步间衔接是数据性 ⟺ 下一步的 args 能由运行时机械得出）：这是全文最值钱的一句，
   而且它可迁移到任何"运行时接续 vs 模型在环"的分界问题。建议保留并升格为独立小节。
2. **§0 的定位表**（四档按模型参与度排，不互相替代）：与 §4.18.12 那条"合并/折叠不冲突、
   各解不同问题"同构 —— 谱系思维是对的，不是选边。
3. **§7 诚实边界**：主动写出"管道的错误定位能力弱于逐步式"、"若 context rot 显著则只该用于
   短链（2~3 步）"、"由测量定不由本提案定"。这是把不能自证的部分交出去了，符合项目纪律。

## 2. Q1（阻断）：P1 判据选错了层面，按现图零合法用例

### 2.1 现有端口图（代码事实）

`CapDef` 的输入/输出是**接口类型名**（`agent_caps.h:224-226`、`agent_fs.h:48/144/248`、
`agent_net.h:93`），11 个能力实际声明的端口：

| 能力 | `in_iface` | `out_iface` | 出处 |
|---|---|---|---|
| `travel.train` | `task.text` | `quote.item` | `agent_caps.c:181` |
| `market.secondhand` | `task.text` | `quote.item` | `agent_caps.c:185` |
| `price.quote` | `task.text` | `quote.item` | `agent_caps.c:189` |
| `plan.merge` | `quote.item`, `quote.item` | `plan.result` | `agent_caps.c:193` |
| `fs.grep` | `task.text` | `fs.hits` | `agent_fs.c:1170` |
| `fs.write_new` | `task.text` | `fs.wrote` | `agent_fs.c:1203` |
| `fs.diff` | `task.text` | `fs.diffed` | `agent_fs.c:1246` |
| `fs.write_apply` | `task.text` | `fs.wrote` | `agent_fs.c:1277` |
| `fs.append` | `task.text` | `fs.wrote` | `agent_fs.c:1302` |
| `http.post` | `task.text` | `http.resp` | `agent_net.c:147` |

### 2.2 按 P1（`cat_out[k] == cat_in[k+1]`）枚举能接的链

- `quote.item` 只有 `plan.merge` 吃 ⇒ `{travel | market | price} → plan.merge` **可接**。
  但 `plan.merge` 要**两个**输入（`quote.item, quote.item`），线性串联只填得进一个
  ⇒ 严格说这条是 **fan-in，不是串联**。
- `plan.result` / `fs.hits` / `fs.wrote` / `fs.diffed` / `http.resp` —— **没有任何能力把它们
  当输入** ⇒ 全是断头。

⇒ **线性管道（长度 ≥ 2、逐步交接）在现有类型图上合法用例数 = 0。**
而 `fs` 族六个能力全都只吃 `task.text`、吐出各自不同的类型 ⇒ **它们互相之间一个都接不上**。

### 2.3 提案举的两个例子都不成立

| 提案处 | 例子 | 为什么不成立 |
|---|---|---|
| §5 | "读三个文件拼摘要、清洗-转换-落盘" | `fs.*` 产出 `fs.hits/wrote/diffed`，**都不是任何能力的输入** ⇒ 类型上接不上 |
| §2.4 | 断点示例里写 `#result fs.read 96B` | **`fs.read` 这个能力不存在**（`grep -rn "fs\.read" tests/` 零命中）。fs 族只有 grep / write_new / diff / write_apply / append |

一个提案的示例和它自己的判据互斥，说明示例不是对着代码写的 —— 这是需要修的第一件事，
因为读的人会按示例去理解机制。

### 2.4 根因：裸串联是**字节级**的，端口是**语义级**的

§2.2 说 v1 只做裸串联（`args[k+1] = result[k]` 全量），紧接着又说"衔接合法性用现有的 TTN 端口判"。
**这两句在层面不同**：

```
裸串联    = 把上游 result 的字节整体塞进下游 args
           ⇒ 判据应该是"下游的 args 方言容不容得下这份字节"
端口类型  = 语义单位（"这是不是一个报价"）
           ⇒ 判据是"上游产出的语义类型是否就是下游要的语义类型"
```

现有能力的 `args` **全部是自由字节**（`pattern`、`path\ncontent`、`path\nbody`），
不是类型化的记录 ⇒ **字节层永远塞得进去，类型层几乎永远不匹配**。
拿语义判据去卡字节操作，结果就是 §2.2 那个零用例。

反过来也危险：**字节层能塞 ≠ 语义上成立**。把 `fs.grep` 的 hits（`path:line:content` 多行）
整体塞进 `fs.write_new` 的 args，第一行会被当 path ⇒ 含 `:` 与 `/` ⇒ `resolve_in_root` 拒绝。
所以"塞得进去"也要按方言判，不能只看长度。

### 2.5 建议的修法：P1 拆成两条，且判据落在方言上

```
P1a（模型侧，语义）：这一步吃不吃上一步的输出，由模型声明，不由我们推。
     理由：§1 判据自己说了——语义衔接的判断信息在模型那里。我们无权替它判。
P1b（我们侧，字节）：下游 args 方言能否无条件容纳整份 result。
     判法：CapDef 声明 accepts_pipe（"我的 args 允许被整体替换"），
           加上方言自身的形状约束（第一段是否是路径/是否允许换行）。
     不匹配 ⇒ 解析期拒整条计划 + stat_pipe_rejected（这条提案是对的，保留）。
```

这样 v1 才有用例：`fs.diff`（args = `path\ncontent`）声明 `accepts_pipe` 之后，
"上游产出一份内容 → 交给 diff 去看差异"就成立了。而现有类型图完全不参与这个判断。

**代价**：`CapDef` 加一个 bool（注册期，零运行时代价）。**但这与提案 §2.3 的
"零新容器、格式零改动"有出入，应当明说**，不能靠"类型图已经建好了"糊过去。

## 3. Q2（阻断）：PAUSED 不是"加一个状态值"，影响面在三个判定点

提案 §4 说"PAUSED 是唯一新状态"，§6 落地清单只列了"WorkItem 加 `cursor`"。
但 `WI_PAUSED` 今天**不存在**（`agent_types.h:22-27` 只有 BLOCKED / READY / RUNNING / DONE / FAILED），
而新增一个状态值的影响面**远大于新增一个字段** —— 字段可以被忽略（默认 0），状态值不行：
漏一个分支就是静默错。三处必须同时处理：

| # | 位置 | 现状 | 加了 PAUSED 会怎样 |
|---|---|---|---|
| 1 | `recycle_tick`（`agent.c:2169`） | `if (status[r] != WI_DONE && status[r] != WI_FAILED) continue;` | **PAUSED 头条目被跳过 ⇒ 永不回收 ⇒ 中间 blob 永不归还 ⇒ P3 自己违约** |
| 2 | 父节点推进（`agent.c:2332-2334`） | `if (ok && status[prow] == WI_BLOCKED && pending[prow] > 0 && --pending[prow] == 0)` | 补计划派生的新子项完成后，**父仍是 PAUSED ⇒ 推不动 ⇒ 计划永远停在断点** |
| 3 | 停滞观测器 | 按"连续 tick 无推进"判 | 提案说"PAUSED 不算停滞" ⇒ 见 Q3 |

⇒ 状态机必须补一条提案里没写的边：**PAUSED ──补完计划──▶ 回到 BLOCKED**（pending 已 += 新条数），
否则第 2 点无解。四行状态机变成五行，且 PAUSED 是**唯一一个会回到非终态的状态**。

## 4. Q3（矛盾）："不计停滞"与"abandoned 时归还"互斥

§3 说 PAUSED-and-abandoned 时整批归还（P3）；§4 说 PAUSED 头条目**不计停滞**。
两句连起来是死锁：

```
不计停滞 ⇒ 永远不会被判"卡住" ⇒ 永远等不到 abandoned
而 P3 的归还条件正是 abandoned
⇒ PAUSED 一旦发生而模型不再回来，中间 blob 就永久泄漏
```

而 `recycle_tick` 的注释已经把这条讲死了（`agent.c:2142-2143`）：
"漏掉递减会让父节点永远 BLOCKED —— 失败不是泄漏内存，是泄漏条目，
而且表现为整个流程静默停住，比崩溃难查得多。"

⇒ 必须有**一个与停滞不同的终止条件**。两个候选：

| 候选 | 判据 | 代价 |
|---|---|---|
| 补计划次数上限（`stat_pipe_exhausted`） | 与 `rounds` 同族，派生时判 | 要定"几次算够"，且撞上限要走失败路径 + 计数，不能静默停 |
| 墙钟超时 | 按 tick 计 | 与"不计推进"冲突：PAUSED 本来就没推进，超时值和停滞阈值是两套口径 |

倾向第一个：**它复用 `rounds` 已有的机制与纪律**（"撞上限走失败路径而不是静默停住"，
`agent.c:1467`），且它是**入口级**的界（一次请求能被补几次），不是时间级。

## 5. Q4：P4 的标题误用了"前缀"

P4 写"**断点续跑不重放前缀**"，内容说的是"前 k-1 步的结果从 blob 引用进 prompt，不重跑 handler"。
这是**两件事**，而且关键字用错了：

- **不重跑 handler**：真的，白拿的，因为结果已在 blob 里。
- **不重放前缀**：**做不到**。补计划是新一轮请求，整份 transcript（system + 历史 messages +
  断点摘要）**照旧全文重发**，KV 前缀该 prefill 还得 prefill。

这正是我们这两天在 `§4.18.14` 抓过的同一类错：**把"计算量 / 窗口占用 / 计费"混成一个词**。
在这里，"重跑 handler"是 CPU 与副作用成本，"重放前缀"是 prefill 与计费成本，
前者省了、后者没省。建议照实写成：

> P4 断点续跑**不重跑已完成步骤的 handler**；但补计划是一次新请求，前缀照旧全文重发
> ⇒ 省的是 handler 与副作用，不是 prefill。要省 prefill，靠的是管道**一次生成**而不是续跑。

顺带纠正 §5 的成本账：它的表只算了"重放工作量"，漏掉轮次。
按提案自己的机制，三步任务失败一次时管道 = **1 轮生成 + 1 轮补计划 = 2 轮**，
逐步 CALL = **3 轮**。⇒ 管道的账比 §5 写的**更有利**，不必那么保守。

## 6. Q5："小模型适配：好"没有依据

§0 的对比表给管道打"小模型适配：好"，与 fan-out 同格。但两者负担不同：

- fan-out：N 条**互不相干**的动作，每条独立合法即可；
- 管道：N 条**必须串得起来**的动作 —— 模型要先在脑内维持"第 k 步产出什么形状"，
  再据此写第 k+1 步，且顺序不能错。

这正好是弱模型最弱的一环（长程一致性）。而 §0 的定位表本身也承认这一点
（逐步 CALL 才是"最好"档）。⇒ 建议改成"**待测**"，并在 §7 加一条：
*若量化/小模型上管道成功率显著低于逐步，则管道只用于强模型档 —— 与折叠展开同理，
目录宽度按模型档调。*

否则这张表会被人当成"管道对小模型友好"去用。

## 8. 建议的 v0.2 方向：堆叠式生成，回退拆成两条轴

需求原话（2026-10-23，用户）：*"我们把内容交给 llm 而非一轮轮调用……做成那种堆叠类型，
只错后面，前面依旧可用，结合了两者的优势，即轮次的可回退以及整轮的少次数。
而且这个应该可以回退，否则前面提到的展开就可能会很难用起来。"*

**这条比提案自己更接近提案想要的**，而且需要的东西已经有一半在代码里。

### 8.1 提案已经是堆叠式的，只是没说出来

`agent_action.h` 的 A4 写：一份产出可以含 N 块，且**"每块的结束位置由它自己的头决定"**
（自定界，v1.13 把 5 字节头改 9 字节换来的）。⇒ **任意前缀都合法可解析**
⇒ 生成侧天然可以按段切断。

§2.4 的"模型补后续计划（重发 3..5）"其实已经是"只错后面、前面保留"，
但提案把它写成一条**执行语义**（P4），没当成**生成格式的性质**。

⇒ 建议改写：把"可分段"从执行语义提到格式性质。判据：

> **段的边界必须落在"不看后缀就能判定合法性"的位置**（前缀可判定性）。
> `CALL|cap\nargs` 自定界 ⇒ 满足。

这条判据同时解释了 §2.2 的失败：**端口类型校验不是前缀可判定的** ——
要判第 k 步接不接得上，得先知道第 k+1 步是谁 ⇒ 它天生不能当段边界判据。

### 8.2 「回退」≠「续跑」，差在触发者

| | 触发 | 方向 | 今天有吗 |
|---|---|---|---|
| 续跑（PAUSED） | **失败** | 从断点往后重发 | 提案新增（Q2/Q3 待修） |
| **回退（rewind）** | **判断**（结果不合意） | 回到第 k 段重来，k..N 作废 | **没有** |

续跑是失败驱动的、单向的；回退是判断驱动的、**可以发生在成功之后**。
而 §1 判据自己说"语义判断在模型那里" ⇒ **回退的发起者只能是模型**，我们只给机制。

⇒ 需要一个 `rewind(k)` 语义：作废 k..N、保留 0..k-1。它比 PAUSED 更强，也更危险。

### 8.3 双轴：生成可回退是无条件的，执行可回退是有条件的

这是这条提议里最必须说清的一件事：

```
生成可回退：段只是字节，作废它不改变世界      ⇒ 无条件
执行可回退：段可能已经产生副作用              ⇒ 有条件，受可逆性限制
```

如果第 3 步是 `fs.write_apply`（覆盖，旧内容不可恢复），回退到第 2 步重来时
**第 3 步的写入已经发生**。⇒ 判据：

> **回退点不能越过最后一个不可逆副作用的段。** 越过就是"以为撤销了，其实世界已经变了"。

这与 §4.18.11 的可回溯性三档是同一条线：**可回退的上界 = 不可归因那一档之前的最后一个点。**
（`fs.diff` / `fs.grep` 天然可回退；`fs.append` 与 `fs.write_apply` 不可；`http.post` 最不可。）

落地：每段结果要带**可逆性标记**；`rewind(k)` 先检查 k..N 里有没有不可逆段 ⇒ 有则**拒绝**
（响亮失败 + 计数），不做"部分回退"。
配 §4.18.12 那条硬判据：**回退的收据必须说出"哪些已经发生了"**，
否则模型以为回退干净了，接着基于"世界在 k-1 段"做下一步 —— 最坏的一类静默错。

### 8.4 段粒度是一个真实两难，而且可量化

```
段越细 ⇒ 回退越便宜（只重发一段），blob 峰值越高（每段都要 checkpoint）
段越粗 ⇒ blob 省，回退要重发一大段
```

`blob_bytes` 已经是白盒账（提案 §2.3 自己提到），所以这个 trade-off **可测**：
同一任务跑不同段粒度，比 `blob_bytes` 峰值 × 回退时重发字节。
⇒ v1 建议取**动作边界 = 段边界**（最细、最自然、零新参数），等测量出来再谈合并。

### 8.5 这为什么是"展开"的前置条件

用户那句"否则展开会很难用起来"，机制上是：

```
展开 = 在上下文尾部插入一段新内容
若生成是"一整块不可分" ⇒ 展开只能发生在块边界 ⇒ 块内无法展开
                         ⇒ 折叠的粒度被生成的粒度锁死
堆叠式 ⇒ 段边界 = 天然的展开插入点 ⇒ 展开粒度与生成粒度对齐、可独立调
```

⇒ 判据：**生成的段边界，就是上下文的可插入点。想让展开灵活，先让生成可分。**
这条应当回填到 `agent.md §4.18.13`，作为折叠展开的一项前置条件。

### 8.6 与 Spark 的类比：映射成立，断点必须写下来

| Spark | 我们 |
|---|---|
| RDD 不可变分区 | 段（不可变，已物化进 blob） |
| lineage | 段的派生关系（第 k 段 args 来自第 k-1 段 result） |
| checkpoint（截断 lineage） | 段结果进 blob（P3"中间 blob 不还"就是保持 checkpoint） |
| 分区丢失只重算该分区 | 回退只重发 k..N |

**断点（这条必须写进文档，否则会被按 Spark 语义误用）**：
Spark 的 recompute 是**确定性的**（同输入同输出），所以重算安全；
我们的"重发"是**模型重新生成**，同一提示两次可能不同 ⇒ **重发不是 recompute，是 retry**。

⇒ Spark 那套能保证"最终一致"；我们只能保证**不重复副作用 + 结果可对账**。
这也是为什么 P4 那条"不重跑 handler"重要：**已执行的不重跑，才能让 retry 只发生在未执行段上。**

## 9. 一句话总结

**提案的形状是对的（一次生成、运行时按序执行、断点续跑），错在把"能不能串"判在了类型层。**
把它挪到方言层（P1a/P1b），再把 PAUSED 当成一个真正的状态（而不是一个值），
然后把"可分段"从执行语义提到格式性质、回退拆成生成/执行两条轴（§8），这份提案就能落。
