**范围**：任务 → 能力 DAG 的算法实现路线，以及 **LLM 在这条链路里的确切位置**。

## 0. 结论先行

一个"分解器"实际是两个问题，文献把它们分得很开，且**两边的算法完全不同**：

1. **候选召回**：从 N 个能力里挑出相关的 k 个 —— 检索问题，BM25 的战场。
2. **组装成 DAG**：把候选连成有依赖的图 —— 规划问题，类型/模式匹配的战场。

把它当一个问题做，只会得到"top-k 能力清单"，那不是 DAG，也没有边。
所以正确的形状是先有**接口类型**（受控词表），再有 DAG；**BM25 负责在 DAG 的每条边上选实现，
或给 DAG 提供路标**。

三条可独立落地的算法（都不需要模型、都不需要网络、都确定性），外加**一个疑点出口**（§6）：

```
task (text)
  │
  ├─[1 切分]  点分名切分 + camelCase 边界 + 小写 + 可选 stem     ← 标识符切分文献
  │
  ├─[2 召回]  倒排索引 + BM25 → top-k 契约条目（路标 / landmark）  ← 你猜的"BM25 这类"
  │
  ├─[3 组装]  IOPE 类型图上双向可达 → 候选 DAG（边 = 数据依赖）    ← 类型导向合成 / HTN / 经典规划
  │
  ├─[4 定型]  HTN 方法库 或 CBR 案例库 择优复用（可以为空）        ← 案例推理
  │
  ├─[5 摘疑点] 有多个合法解而算法无权选的地方 → Ambiguity[]        ← 神经符号（§6）
  │              ↓ 只有非空时才问 LLM；答案是一个索引，不是一段计划
  │
  └─[6 选择]  成本档 / 信任天花板 / 偏好 → 定一条                  ← L3 消解路由前移（§6.5）
                                                                   ↓
                                                          plans / leaves 两表（L1 的产物）
```

**最重要的一条**：第 5 步是**可空的**。唯一解时整条链**零 LLM 调用** ——
算法覆盖率因此是一个可观测、可增长的量（§6.6）。

**档位是显式的**（§6.10）：`RULE` / `TEMPLATE`（零 LLM）/ `SELECT`（只答索引）/
`GENERATE`（补约束），按 LLM 参与度递增，作为 `plan_search` 的入参存在；
**默认只取 `RULE` 或 `TEMPLATE`**，`SELECT` 需"档 0/1 给不出唯一解"才升，
`GENERATE` 更严且**跑完必须回 `SELECT`**。另有一条结构性不变式：
**「LLM 自由生成整图」没有对应档位 —— 不是不推荐，是不可表达。**

## 1. 第一段：候选召回 —— BM25 的战场

### 1.1 实证：在"小而结构化"的工具空间里，BM25 打平甚至超过语义嵌入

这一条与 RAG 的常识相反，值得单独看。四处独立证据（两处 arXiv、两处工程实测）：

| 来源 | 规模 | 结果 |
|---|---|---|
| 生产案例（博客，~140 个 MCP 工具） | 140 工具 / 200 query-tool 对 | **BM25 top-1 81%** vs 嵌入 **64%**；hybrid（0.7 语义 + 0.3 BM25）**78% —— 比纯 BM25 还差** |
| Vstorm 8 策略评测（51 工具 / 16 类） | one-shot 准确率 | all_tools 99%（上界）· regex 95% · cross_encoder 95% · pinecone 94% · **BM25 93%** · milvus 90% · hybrid_pinecone **89%（垫底）** |
| ToolScope（arXiv 2510.20036） | Seal-Tools，CSR@5 | BM25 **0.544** vs Dense **0.548** —— 几乎相同 |
| ToolDreamer（arXiv 2510.19791） | ToolRet，N@10 零样本 | BM25 **27.25** · all-MiniLM-L6-v2 29.53 · text-embedding-3-small 32.72 · **Qwen3-8B 35.81** |

读法：
- BM25 与**中小**嵌入（MiniLM / ada-002 级）在工具检索上**同一档**；
- 只有上到 Qwen3-8B 级的大 dense 才拉开约 20%（MRR）；
- **最简的关键词法（regex）与最好的语义法并列**，而**混合检索反而垫底**。

### 1.2 为什么 —— 这个空间的性质与 RAG 不同

失败模式是镜像的：

- **BM25 的盲区**是词汇不匹配（"laptop won't turn on" vs "notebook fails to boot"），零词重叠 → 0 分。
- **嵌入的盲区**是把措辞压成意义，于是 `E4022` 与 `E4023` 在向量空间几乎重合——**恰好抹掉 BM25 赖以生存的精确性**。

工具/能力检索是**精确标识符检索**的典型场景（错误码、SKU、函数名、verbatim 术语），不是 paraphrase 场景。
且工具描述极短（< 50 token）、结构高度同质，verb-noun 的软语义会**稀释判别性关键词**——
生产案例里"list the open issues for this repo"召回了 `slack_search_messages` 而非 `github_list_issues`，
就是因为 `issues` 这个唯一判别词被稀释。

**对 cxf 的额外理由**（比上面所有实证都硬）：
BM25 的整条查询路径是 **CPU-only、无矩阵乘、无 GPU、无浮点模型**；得分**可逐项追溯到具体 term**——
每一分的来源是可打印的。这与本项目的白盒性/确定性目标是同一件事，不是巧合。

### 1.3 反直觉但关键：hybrid 常常**更差**

四处证据里 hybrid 三处垫底。机制很具体：RRF（reciprocal rank fusion）在两个排序器**意见不一致时求平均**，
把正确的第一名拉到 top-k 之外。工具空间小且结构化，两条排序器的分歧是**噪声**而非信号。
⇒ **支持先做纯 BM25，不要急着上嵌入**；要混合也该是串行（BM25 召回 → 重排），不是并行融合。

### 1.4 一个白捡的红利：把 schema 的字段名也索引进去

生产案例里，把 `input_schema` 的 property 名（`repo_id`、`branch`）也纳入索引，
是准确率从 64% 抬到 81% 的关键之一 —— **因为字段名才是判别性最强的部分**。
本项目的 `CapDef.in_schema` / `out_schema` 天然扮演这个角色，
但现在是**散文**（"商品描述（本地缓存命中时用本地解析）"），索引价值为零。
⇒ 见 §5：这是把 `*_schema` 升级成**受控词表**的第一条动机。

### 1.5 何时不值得做（诚实边界）

arXiv 2026 的代码检索研究给出一个量级门槛：**约 1000 万 token**。
低于它，"让模型读完全部目录"的准确率仍具竞争力，BM25 只增加复杂度、无净收益；
高于它，BM25 的优势一路扩大到约 20 个百分点。

对本项目：单 rank 空间内能力数是**百级**，远低于门槛。所以诚实的表述不是"BM25 更快"，
而是三条**结构性**理由：
1. 它是**唯一能脱离 LLM 单独验证**的一段（可写断言、可复现、无外部依赖）；
2. 它是 §7.1 那个"目录检索本身又是一个能力"的**第一个具体实现**；
3. 它是跨节点联邦目录（§7.2）的前提——79K 能力的库无法全量进上下文
   （full-library prompting 约 43M 输入 token / 请求 vs top-10 约 27.7K）。

### 1.6 BM25 公式与变体（纯文本）

```
score(q, d) = Σ_{t ∈ q}  IDF(t) · tf(t,d)·(k1 + 1) / ( tf(t,d) + k1·(1 − b + b·|d|/avgdl) )

IDF(t) = ln( 1 + (N − n(t) + 0.5) / (n(t) + 0.5) )
```

- `k1` 控制词频饱和速率，IR 教科书建议 `[1.2, 2.0]`；`b` 控制长度归一化强度，默认 `0.75`。
- 变体：Robertson（原始，需把 IDF 截到非负）/ ATIRE / BM25L / BM25+ / Lucene。
  缺一不可的理由：`tf` 饱和与长文档惩罚对**短且等长**的目录项几乎无意义
  （我们的 `desc` 都是一行）——**我们的场景里 `b` 应当调低甚至归零**，
  因为它惩罚的是"描述写得详细"这一优点。这是个反直觉但重要的判断。
- 全部所需量（`N`、`n(t)`、`|d|`、`avgdl`）都在**注册期**算好 → 查询期只做乘法 + 加法，
  与 §4.6"门控必须远便宜于专家"的纪律同构。**索引在 `registry_sync` 里建，查询期零分配。**

## 2. 第二段：DAG 组装 —— 这是 planning，不是 retrieval

### 2.1 HTN：**分解器**这个词的原始含义

HTN（Hierarchical Task Network）与经典规划的分野：
**HTN 是把高层任务归约到原子任务，经典规划是拼装动作以达成目标。**

- **方法（method）** = 一个映射：复合任务 → **偏序**的子任务网络 + 约束集。
  规划器递归展开复合任务，直到全是原子任务，再做冲突检测与消解。
- **SHOP2**：全序前向分解，"规划期与执行期交错"，实践中很多情形是**线性时间**。
- **有序任务分解变体**：方法按**声明顺序**优先，线性推进、**不回溯**。
  ⇒ 这正是 cxf 要的形状：**确定性、无回溯、可断言**。
- **复杂度**（Erol / Nau / Hendler 1990s）：无限制情形下**不可判定**；
  受限（**方法层次无环**、有限域）为 **EXPTIME-complete**。
  ⇒ 与 §10.2 的"降级链无环性是**注册期不变式**"是完全同一条哲学：
  **把成环从运行时的担心变成注册期的编译式错误。**

**与我们的映射**：`CapDef` 的点分命名空间天然是方法库的骨架
（`travel.*`、`price.*`、`plan.*` 就是"域"）；`CapImpl.tier` 已区分 script / llm。
所谓"写死计划表"其实就是**退化到单条方法的 HTN**——升级路径是让方法本身成为数据。

### 2.2 经典规划（STRIPS / PDDL）：IOPE 与一个早被指出的难题

服务 = 带 IOPE（Input / Output / Precondition / Effect）的 action，规划 = 找从初态到目标态的序列。
OWL-S 是唯一直接声明与 AI 规划挂钩的服务描述语言，映射到 PDDL 是**直译**。

**McDermott 早就指出的关键难题**：closed-world assumption 下，"**新获取的信息**"无法用真值字面量表达
（字面量不在当前状态 = 假，于是"我拿到了一个新 ID"不可说）。解法是**把两类东西分开**：

- **I/O 参数**：可复用、**可被多个服务重复消费**（可复制 → 这就是 DAG 的 fan-out）；
- **世界状态**：一次性，执行即旧态消失。

⇒ **这就是"为什么是 DAG 而不是链"的理论根据**：数据可 fan-out，状态不可。
我们的 `WorkItem.parent + pending` fan-in 已经实现了这个语义（DAG 写在数据里），是同一个东西。

### 2.3 一个可以直接搬过来的手法：信息类在规划期执行

OWL-S → SHOP2 的映射里，最值得抄的一条工程手法：

> **信息获取类（information-providing）服务在规划期就执行；改变世界类（world-altering）服务只做投影 / 模拟。**

理由是把不确定性和搜索空间**在规划期消掉**（"book-keeping"算子 / SHOP2 求值式前置条件）。

**这是 `CapTrust` 在 20 年前的同构物**：

| OWL-S | cxf |
|---|---|
| information-providing | `CAP_TRUST_LOCAL` / `CAP_TRUST_IO`（读本机 / 出网读） |
| world-altering | `CAP_TRUST_WRITE`（写盘 / 支付 / 对外副作用） |

⇒ **一个值得明确写进 §6 的越权许可**：分解期允许**实际执行**信任级 ≤ IO 的叶子，
把返回值当**常数**填进后续叶子（消解不确定性）；WRITE 只能留在执行期。
这不是偷跑——是有 20 年理论依据的分工，并且它正好解释了为什么 trust 必须是**三级而不是两级**。

### 2.4 CBR（案例推理）：检索"最容易适配的"

- **核心反直觉**：case-based planning 里，检索目标不是"**最相似**"，而是"**最容易适配的**"
  （adaptation-guided retrieval，Smyth & Keane 1995；Bergmann 等）。
  相似度评估的目的是**预测复用代价**，代价低才算相似。
- **DIAL** 除了存计划，还存 **adaptation case**（适配 episode：适配目标 + 初始计划 + 实际改动）。
  ⇒ **这是 L1 缓存层的理论依据**：§7.1 的"目录世代号兼任缓存键"就是 CBR 的 case indexing；
  "记录改法"就是存 adaptation case。
- **一条负面结论（必须知道）**：Nebel & Koehler 1995 证明 **MODSAT 在最坏情形下不比 PLANSAT 更容易**
  ——因为**模板计划可以是空的**。翻译过来：**复用不保证省事**，
  所以"有 cache 就用"必须配一条**廉价的可适配性估计**，否则不如重新规划。

### 2.5 拆到哪一层停：**原子 ≠ 一次能力调用**

§2.1 那句"递归展开直到全是原子任务"是 HTN 的标准说法，但它**没定义"原子"**。
默认读法是"一次能力调用"——**那个读法是错的**，而且错得很安静。这一节把"原子"钉死。

**先把两种"闭合"分开。** "以闭环为单位拆分"这个主张，取决于"闭"指哪一种：

| | 运行时记账闭合 | 语义闭合 |
|---|---|---|
| 判据 | 有 parent、`pending` 归零、产出终值 | 做完了没有，**不看后续单元就知道** |
| 在 cxf 里 | **每个 row 自动成立**（`agent.h:328` 的控制流标记 + `pending`） | **不自动成立**，要分解期保证 |
| 按它拆的后果 | 等于没约束（"以行为为单位"和"以句子为单位"都对，所以都不构成指引） | 每个叶子可独立验收、可独立重跑 |

⇒ **主张成立，但要按第二种理解**。按第一种理解，这句话只是把"每个 WorkItem 是一个 WorkItem"重说了一遍。

**语义闭合的三条可判定要求**（缺一条就不是闭环，是碎片）：

1. **独立验收**：这个单元的终值**本身**就是答案，不是"下一步的输入"。
   反例：`fs.grep` 找行号 → 另一个能力按行号改。第一个的产出只是中间量，它没有自己的正确答案。
2. **独立重跑且代价可声明**：能回答"重跑一次付多少"（A1 `CapRerun` 的三种：整棵子树 / 一条边 / 一次调用）。
   答不上来 ⇒ 它的边界没有落在副作用边界上。
3. **副作用同生共死**：一个闭环里不能出现"一半生效"。要么全成，要么全不成。

**由这三条得到拆分的两个边界：**

```
下界（不许再往下拆）：写操作的原子边界 —— 一条逻辑写不能跨两个闭环
上界（必须继续拆）：目录里没有能力能整体承接 —— 有就停，没有就说明它还是复合的
```

**下界为什么是硬的（这是本节唯一必须论证的地方）。**
运行时的 `pending` 在子项**失败时也递减**（`agent.c:2107`：`FAILED → 不追加内容，但必须仍然
递减父节点的 pending`；不递减就永远等不到 S'，表现为整个流程静默停住）。
于是"改 A 行"成功、"改 B 行"失败 ⇒ `pending` 照样归零 ⇒ 续跑 ⇒ 终值 blob 照样生成。
模型读到一份**看起来完整**的结果，而盘上是半改的。

关键在于：**运行时无法区分这两种情况** ——
"失败了一条，但语义仍完整"与"失败了一条，语义已残缺"。它没有语义，只有计数。
所以这个责任不可能落在运行时兜底，**只能在分解期拒绝产生那样的边界**。
这正是"成熟不是用例通过，是任意操作顺序下不静默错"在拆分粒度上的形态。

**这条现在测不出来，得说清楚**：目录里只有只读能力（`fs.grep`），
没有第二个带副作用的实现 ⇒ "半写"这个形状无观测对象。上面那句是从
`recycle_tick` 的不变式（失败也递减 `pending`）**推**出来的，不是实测的。
**触发条件是出现第一个 WRITE 能力**：那时要补一个用例 —— 两个写叶子、第二个强制失败，
断言父节点的终值里**必须带有"其中一条失败"的痕迹**，否则就是本节说的静默错。
在那之前，这只是分解期的一条禁令，没有反面证据也没有正面证据。

**上界与 §2.3 是同一件事的两面**：§2.3 说"读类叶子可以在分解期执行"（trust ≤ IO），
本节说"写类叶子不能跨闭环拆"（WRITE）。两条合起来才是 trust 三级的完整用法 ——
**读可拆到细，写只能拆到原子**。

**这个判定天然只有一半是机器可判的，别想一次判完：**

| 一半 | 可判性 | 落点 |
|---|---|---|
| **类型够不够**（有没有能力的入参能覆盖这个叶子） | 机器可判 | 复用 `chain_reachable`（`agent.c:1241`）—— 分解期就该跑一遍，而不是等运行时 `intent_ok` 才拒 |
| **语义超没超**（这个子任务是不是大于那个能力的 `desc`） | 不可判 | 进 §6 疑点出口，让消解方（人 / 约束 / 分类器）回答 |

⇒ 于是"叶子是不是真原子"这个断言**必须拆成两半写**。把它当成一个全可判的断言，
就会逼出"用 LLM 自查"（§6.11 已用 PlanBench + self-critique 实证否掉）。

**一条推论：幂等键的作用域 = 闭环的粒度。**
`CapRerun` 要回答"重跑这个单元会不会造成第二次副作用"，而"这个单元"就是闭环。
两者一旦不同住（键挂在单次调用上、边界画在闭环上），就会出现
"重跑时键相同但边界更大"的静默重复写。**两个必须一起变的值，让它们同住一个结构** ——
所以将来 `CapRerun` 的幂等键挂在 row / 子树上，不挂在 `CapImpl` 调用上。

### 2.6 可逆性不是操作的内禀属性

上面把"写"当成一个类别讨论，容易滑进一个错的分级："读安全 / 写相对安全 / 组合才危险"。
三句都不准确，而它们是**同一句错话**的三个版本。正确的那一句是：

```
可逆 ⇔ 存在一个逆操作，且**执行它所需的信息在正操作完成后仍然存在**
```

这条判据里没有"读 / 写"，也没有"单 / 组合"，只有**信息还在不在**：

| 操作 | 逆操作 | 逆操作需要的信息 | 完成后信息还在？ | 判定 |
|---|---|---|---|---|
| 读 | 什么也不做 | 无 | — | **可逆** |
| 写到**本操作创建的**新路径 | `unlink` | "这路径是我建的"（路径名本身） | 在 | **可逆** |
| 追加写 | truncate 到原长度 | 原长度（调用方手上才有） | **只在调用方** | 半可逆 |
| 覆盖已有文件 | 写回旧内容 | **旧内容** | **已被覆盖破坏** | **不可逆** |
| 删 | 恢复文件 | 全部内容 | **没了**（除非有版本库 / 快照） | **不可逆** |
| 出网副作用（转账 / 发布 / 发消息） | 补偿操作 | 对方的配合 | 不在我们手里 | **不可逆** |

**三处必须纠正的说法：**

1. **"单行为安全"不成立。** 覆盖一份配置文件是单个 `write`，代价是下次启动起不来；
   单个 `POST` 能转账。**单行为之所以看起来安全，只因为它最常见的形态是"写一个自己刚建的文件"。**
2. **"删能复原"不是通用判断。** `unlink` 之后内容不在任何地方 —— 它可逆**当且仅当**
   这片盘被版本控制 / 快照 / 备份覆盖。**可逆性是存储系统的属性，不是操作的属性**：
   同一个 `rm` 在 git worktree 里可逆，在 `/tmp` 里不可逆。
3. **"组合才有风险"把风险归错了位置。** 组合确实有两种风险，但都不是"写本身安全"：

| 组合风险 | 机制 | 解法（不是权限） |
|---|---|---|
| **半完成** | 两个各自可逆的写，第一个成功第二个失败 ⇒ 系统停在没人声明过的中间态 | 闭环边界（§2.5） |
| **权限合成** | 读敏感 + 出网写 = 外泄。两个能力各自都在天花板下，组合起来等价于一个没人声明过的能力 | **污点**，见下 |

**★ 由此得到一条 cxf 里必须先写下来的判据：`trust` 挡不住组合，因为它是能力级属性。**

`CAP_TRUST_LOCAL / IO / WRITE` 说的是"这个能力能碰哪一档东西"，而"读出的字节流去了哪里"
是**数据级**属性。每个能力都能合法，数据流向仍然可以非法 —— 挡这件事要的是
**污点标记**（LOCAL 读出的字节不得进入 IO/WRITE 能力的入参），不是第四级 trust。

**但它现在零代码，也不该建**：目录里只有只读能力，没有出网写能力 ⇒ **没有真实调用方**，
一条约束会写成"永远成立"从而永不被验证。触发条件：**第一个 `CAP_TRUST_IO` 的写能力
（或第一个把 LOCAL 数据送出去的协议能力）落地时**，在同一个提交里加进来 —— 因为那时
它才第一次有违反的可能。

## 3. 第三段：接口对齐 —— 把候选连成边

### 3.1 类型导向合成：把库变成一张图

这是**把 BM25 的输出变成 DAG 边**的那一段机制，也是本调研里对本项目**最有价值**的一条。

- **组件式合成（component-based synthesis）**：目标是找一组组件的**组合**来实现给定任务；
  **类型导向**时，任务与组件都用类型刻画。
- **可扩展做法 —— 类型转移网络（TTN, type transition network）**：
  每个**类型是一个状态**，每个**组件是一条从输入类型到输出类型的定向边**；
  合成就退化成**在图上找一条从查询输入类型到输出类型的路径**。
- **多输入组件** ⇒ 图升级为 **Petri 网**（hyper-edge：多个输入 state → 一个输出 state）。
- 系统谱系：Prospector（一元，图）→ SyPet（n 元，Petri 网）→ TYGAR（多态，抽象类型）
  → INSynth（succinct types）→ **APIphany**（PLDI'22，REST API，从 OpenAPI + 执行轨迹挖语义类型，
  29 个基准解出 23 个）。
- **解法排序**：语法规格通常有歧义，必须对候选排序；常用手工或学到的排序函数，
  APIphany 甚至**按执行结果**排序（"是否总是失败"等启发式）。

**对本项目的直接含义（五条）**：
1. 若 `in_type` / `out_type` 是**受控词表里的稠密 id**，"任务 → 能力 DAG"就退化成
   **图上可达性**——最简形态甚至不需要搜索：从目标类型**反向**走前驱边（反向邻接索引）即得候选 DAG。
2. **谁来做这条边上的实现，是 MATCH 的事**——这正好落在已有的两层拆分上，L1 完全不必知道。
3. **Petri 网语义我们已经在跑**：`WorkItem.parent` + `pending` 就是 token 计入/放出。
   所以"多输入"不是新机制，只是新表述。
4. TTN 是**注册期构建、可静态断言无环**的 —— 与 §10.2 / HTN 方法层次是同一个不变式家族。
5. **两张图互为对偶（line graph）**，这点必须说透，否则"在哪张图上搜"会一直含糊：
   **类型图**（节点=类型，边=能力）用于**分解期倒推**；**能力图**（节点=能力，边=类型）
   用于**执行期 fan-in**。**必须在类型图上搜** —— 因为分解期的已知量是**类型**
   （目标类型来自检索、入参类型来自外部），只能从类型倒推能力。**这就是反向邻接
   （`prod_head`）存在的实质理由**，不是为了对称好看。
   ✅ **已落地**：`IfaceDef` / `CapDef.in_iface[]` / `cat_out` `cat_in` / `prod_head+next`
   `cons_head+next`，注册期不变式 6/7/8，见 `docs/agent.md` §10.6。

### 3.2 模式匹配（schema matching）：当 in/out 不是严格类型

如果 in/out 是"字段/文档"而非严格类型，接口对齐就落到 schema matching 语料上：

| 系统 | 机制 | 可取的 |
|---|---|---|
| **Cupid** | 语言匹配（形态归一 + 公共前后缀 + 同义词表）+ 结构匹配（按**叶子加权**的树匹配），加权阈值出映射 | 结构性加权 |
| **COMA** | **可组合的匹配器库**（6 基本 + 5 混合 + 1 复用）+ 组合框架；schema 内部编码为 **DAG**，元素 = 路径；基础手法 = **affix / n-gram / edit distance**；支持迭代 | **matcher 做成可组合库** —— 概念上等同于把匹配器做成 `CapImpl` |
| **Similarity Flooding** | schema 当有向标记图；从字符串比较起步，**把相似度向邻接节点传播**，迭代到不动点 | 传播式（互为上下文的字段应相似） |
| **S-Match** | 只用 schema 层 + 外部词表 + **命题可满足性**；**全程无人工介入** | 无人工介入 = 可自动化断言 |
| **NOM** | 17 条规则显式编码本体知识（父子概念/属性） | 规则可枚举、可审计 |
| **QOM** | 牺牲少量质量换效率：**放弃完全两两比较**，改不完全自顶向下 | 与我们"宁可 O(n²) 也要可读"的取舍相反，需权衡 |

**关键可落地性**：Cupid / COMA 的**初级手法全是字符串级**（affix / n-gram / edit distance），
**纯 C、零分配、可离线预计算**。它们是"我们先做简单的那一半"的正当依据，
而不是"我们做不了复杂的所以凑合"。

### 3.3 标识符切分：`travel.train` 本质是代码标识符

能力名是点分标识符，切分规则直接借**代码检索**的成熟语料：

- 拆分算法谱系：**Conserv**（参考实现：下划线 / 数字 / camelCase 切）→ **Greedy**（在词典上找最长前/后缀）
  → **Samurai**（**挖掘源码词频**切分；局部 + 全局频率表 + 常见前后缀表）
  → **GenTest**（生成全部切法 + 打分）→ **Ronin**（Spiral 库，JOSS 2018）。
- 缩写扩展：Basic（Lawrie）→ **AMAP**（从源码挖掘缩写展开，按方法/程序/全局三级上下文选）
  → Normalize。
- 现成库：`casics/spiral`（Python）、`eroatta/token`（Go）。

**必须记住的实证**：BM25 在代码上要与嵌入打平，**必须**做 camelCase / snake_case 拆分，
且要**同时保留子 token 与原形**（两种都进索引）、**给路径更高的权重**、**保留有意义的特殊符号**
（`.` 在 `__init__` 里有意义，丢弃它等于丢掉语义）。

**对本项目的具体映射**：`price.quote` 与 `market.secondhand` 的点分切分规则极简
（`.` + 大小写边界），且**索引可在注册期一次性建好**，查询期零分配。
"保留特殊符号"这条尤其贴切：**点号本身就是域层级，绝不能先当空白丢掉**。

## 5. 我的判断（有观点的，不是选项罗列）

1. **BM25 是流水线的第一段，不是分解器。** 把 BM25 当分解器只能得到 top-k 清单。
   缺的那一段叫 planning，算法核心是 TTN 上的可达性。**先有类型词表，再有 DAG。**
2. **但 BM25 该先做**，因为它是唯一的"能脱离 LLM 独立验证"的一段：
   无网络、无模型、确定性、每一分可追溯到 term —— 正是本项目要的形状。
3. **cxf 的形态是"三小一大"，且大模型只吃疑点**（详见 §6）：
   - **小**：BM25 倒排索引（注册期建、可增量）
   - **小**：TTN + 反向邻接（注册期建、可断言无环）
   - **小**：HTN 方法库 / CBR 案例库（**允许为空**，退化成纯 TTN 搜索）
   - **大**：LLM —— **不是兜底，是疑点消解器**。算法照常搜，只在
     "有多个合法解而算法无权选"的地方问它，且**它回答的是一个索引，不是一段计划**。
   - **一条补充口径（§6.9）**：它的**输出形态可以更宽**——也可以让它出整张草图。
     分界线不是"能不能出图"，而是**"这张图的正确性算法能不能判掉"**；
     能判掉就是多了一路召回器，判不掉就必须缩回"只回答一个索引"。
4. **不要急着上嵌入**：四处证据一致显示 hybrid 在工具检索上常常**比纯 BM25 差**。
   要混合也该是串行（BM25 召回 → 重排），不是并行 RRF 融合。
5. **分解期允许执行读类叶子**（trust ≤ IO），把返回值当常数消解不确定性；
   WRITE 只留在执行期。这条有 OWL-S/SHOP2 的分工作依据，**正是 trust 三级而非两级的理由**。
6. **我们场景里 `b` 该调低甚至归零**：BM25 的长度归一化惩罚的是"描述写得详细"这一优点，
   而我们的目录项都是一行等长描述。这是一条与教科书默认值相反的判断。
7. **复用不保证省事**（Nebel & Koehler）：MODSAT 最坏情形不比 PLANSAT 容易，因为模板可为空。
   ⇒ "有 cache 就用"必须配**廉价的可适配性估计**，否则重新规划更划算。

## 6. 神经符号形态：算法 + 疑点 + LLM + 选择

**本节修正 §5 第 3 条。** 原方案是"算法当链头、**整体失败**才降级到 LLM" ——
那是**粗粒度回退**：只要搜索失败一次，已算对的部分全部作废，从头让模型重来。
更好的形态是**细粒度定点求助**：算法照常搜，把**它无权决定的那些点**单独摘出来交给 LLM。

### 6.1 三档输出，而非成功/失败两档

关键认识：**"算法算不出来"其实分两种，性质完全不同。**

| 算法产出 | 含义 | 谁定 |
|---|---|---|
| **唯一解** | 只有一条路径能走 | 算法直接派发，**零 LLM 调用** |
| **疑点（多个合法解）** | 有 ≥2 个合法解，算法**无权**排序/选择 | LLM（或有权限的人）**只在这里介入** |
| **无解** | 没有路径 / 缺能力 | FAILED，或走 flywheel 造新能力 |

**疑点 = 合法歧义（legal ambiguity），不是失败（failure）。** 这个区分是整个形态的支点：
把"疑点"混进"失败"，就退化回粗粒度回退；只有分开，LLM 才只被用在它唯一能赢的地方。
（上面是**操作定义**；**本质定义**见 §6.7 —— 判据的载体，那里还有一个把"什么算疑点"
变成**纯算法判定**的公式，以及为什么 LLM 是一个"自带退出路径"的组件，见 §6.8。）

### 6.2 文献对应（这条路线不是新发明）

| 本方案的说法 | 文献里的名字 | 关键机制 |
|---|---|---|
| 算法只做必须的承诺，其余留成疑点 | **least-commitment planning**（SNLP / UCPOP 一脉） | 最小承诺：不做出无从判断的决定，把顺序/绑定/实现选择**延后** |
| 算法给骨架、疑点是洞 | **sketch completion / hole filling** | 骨架 + 洞，洞由外部填 |
| 只在打分接近时才问 | **query-by-committee / uncertainty sampling**（主动学习） | 委员会意见不一致才询问 oracle |
| 符号层给离散骨架、把连续部分的洞交出去 | **TAMP**（任务与运动规划） | 符号层无法判定连续可行性（碰撞/可达），洞交给采样器 |
| LLM 只做候选生成、外部做验证与反馈 | **LLM-Modulo**（Kambhampati 一派） | LLM = candidate generator，符号层 = verifier |
| 无解则把错误反馈 LLM 重新规划 | **LLM+P** | **整体回退，粒度粗** —— 就是要避免的那一档 |

### 6.3 疑点必须是结构化的选择题，不能是自然语言描述

**这是本形态能成立的技术前提。** 如果算法交给 LLM 的是一句"我不确定该用哪个"，
那就退化成了把整个问题丢回去 —— 和粗粒度回退没有区别。正确做法是：

```c
typedef struct Ambiguity {
    uint32_t kind;      /* AMB_GOAL / AMB_IMPL / AMB_PATH / AMB_ARG */
    uint32_t slot;      /* 疑点在计划的哪一处（leaf index / 第几个输入端口） */
    uint32_t cand[AMB_CAND_MAX];   /* 合法候选，全是稠密 id */
    uint32_t n_cand;
} Ambiguity;
```

**候选必须带上"渲染后的名称 + 一句话描述"，不能只给 id**（理由见 §6.8）：
模型的世界知识里**没有你的目录** —— 它有"比价"的常识，却分不清 `market.secondhand` 与
`price.quote` 差在哪，除非你把这两个候选的描述一起递过去（就是 §7.1 那份渲染过、消毒过的）。
**光有世界知识不够，目录知识必须随疑点一起走。**

于是 LLM 的活被压成：**在一个受限的、可枚举的选项集合里选一个索引。**

三条红利（都可以写成断言）：
1. **输出可校验**：返回的索引必须在 `[0, n_cand)` 内，越界立刻报错 —— 与"响亮失败"一致；
2. **任务被降级**：从"开放式规划"降到"受限选择"，这正是文献里模型擅长的那一档
   （§3 Beyond ReAct：SFT 帮工具选择、RL 才帮连边 —— 选择比连边容易）；
3. **可缓存**：同一 `(候选集合, 上下文)` 的答案结晶一次即可复用 —— 见 §6.6。

### 6.4 疑点的四种来源

| kind | 从哪来 | 例 |
|---|---|---|
| `AMB_GOAL` | BM25 的 top-k 分数接近，目标类型并列 | `plan.result` vs `price.item` 都是合理目标 |
| `AMB_IMPL` | 同一类型有多个能力产出，且成本/信任档接近 | `price.item` 由 `market.secondhand` 还是 `price.quote` |
| `AMB_PATH` | 类型图上有多条等价路径（长度、成本接近） | 经 `quote` 还是经 `secondhand` 到 `plan.result` |
| `AMB_ARG` | 参数能从文本正则抽出 vs 抽不出 | "预算 3000" 可抽；"比价" 抽不出偏好 |

**必须配疑点预算**：k 个独立分叉就是 2^k 个候选，会组合爆炸。所以要有
（a）**上限**（`AMB_MAX`）、（b）**排序**（哪个疑点最影响结果）、（c）**优先级**
（`AMB_GOAL` > `AMB_IMPL` > `AMB_PATH` > `AMB_ARG`：上层错了下层白解）。
这与 §4.7 的 `max_iters` 是同一类护栏 —— **护栏不是可选的美化，是让机制可终止的条件**。

### 6.5 "然后再选择"：这就是 L3 消解路由，只是前移了一层

`docs/agent.md` §4.6 已经把 L3 定义为"**多路结果 → 最终方案**，top-k + 偏好加权选择"。
本形态只是把它的**输入**从"执行结果"提前到"计划候选"：

| | 执行前选（本形态主路径） | 执行后选（§4.6 L3 / §4.7 对冲） |
|---|---|---|
| 代价 | 便宜（不跑就选） | 贵（要跑多个） |
| 依据 | **声明**（cost / trust / 目录元信息） | **实测**（真延迟、真结果） |
| 定位 | 主路径 | 补救：结果不满意时才用 |

**两级不冲突**：主路径执行前选，执行后选留给真正需要的那一档。这样既不付无谓的执行代价，
也保留了"跑了才知道"的退路。

### 6.6 白捡的红利：疑点消解是 flywheel 最自然的入口

`docs/agent.md` §7 的 flywheel 一直缺一个**精确接口** —— 系统在什么时刻该写一个新工具、
该结晶一条规则。**疑点就是那个时刻**：

- 每回答一个 `AMB_IMPL`，就产出一个可结晶的 `(候选集合, 上下文) → 选择` 对，
  下次同类疑点直接命中（复用 §7.1 的世代缓存键）；
- 某类疑点**反复出现**，说明算法缺一条判据（该加规则），或目录缺一个更对路的能力（该造工具）；
- 于是 **`疑点计数` 就是 flywheel 的驱动信号**，比 `stat_llm_calls` 更精确 ——
  后者只说"调了几次模型"，前者说"**为什么调**"。

### 6.7 疑点的本质：看**判据的载体**在哪

§6.1 给的是疑点的**操作定义**（"有多个合法解，算法无权选"）。这里给**本质定义**：

> **疑点 = 该决策的正确性依赖于符号层里不存在的信息。**

用这个定义，整份设计可以被三句话统一 —— 不看"谁更聪明"，**只看判据住在哪里**：

| 判据的载体 | 例子 | 谁来做 | 可判定性 |
|---|---|---|---|
| **符号层**（类型 / 成本 / 信任 / 容量 / 名字相似度） | 两个实现成本差 10 倍 | **算法，永不问模型** | 直接比较 |
| **自然语言**（用户那句话的语义、世界知识） | "比价"该走二手还是官方报价 | **LLM**（即疑点） | 见下 |
| **你自己的数据**（同类疑点做过 N 次） | 这个 (候选集合, 上下文) 上次选了 2 号 | **缓存 / 分类机，取代 LLM** | 查表 |

第二行的**可判定性**是关键：算法怎么知道"判据不在符号层"？
—— **把所有候选在符号层的所有特征上算一遍；若它们全都不可分（或边际低于阈值），
那"正确性依赖符号层外信息"就成立。** 这就是 query-by-committee 的机械形态：

```
margin = score(top1) − score(top2)        /* score 只用符号特征 */
margin > τ  →  唯一解，算法直接定（零模型调用）
margin ≤ τ  →  疑点，交给消解器
```

三条推论：
1. **疑点的判定本身是纯算法的**，没有任何模型参与 —— 疑点是算法**算出来的**，不是感觉出来的；
2. **τ 是唯一需要调的参数**，语义清晰：**"符号层能分辨到多细"**；
3. 于是 **LLM 的调用量变成一个连续旋钮**：τ 调低 → 疑点多 → 更准更贵；
   τ 调高 → 疑点少 → 更快更可能选错。**这是一条 cost/quality 曲线，不是一个二值开关。**
   （对照 §6.1：粗粒度回退方案连这条曲线都不存在，只有"全用"或"全不用"。）

### 6.8 为什么用 LLM：它是唯一**自带退出路径**的组件

用户的原话是准确的：**"LLM 是一个无需数据驱动的、可先验使用的算法"**。
形式化地说，疑点消解是一个多分类问题：

```
输入 x = (kind, slot, 候选集合的符号特征, 渲染过的候选描述, 上下文)
标签 y ∈ {0 .. n_cand−1}
传统做法：需要 (x, y) 数据训练 p(y | x)
LLM 给的： p(y | x, 世界知识先验)     —— 不用你的任何数据
```

**所以 LLM 的价值不是"更聪明"，而是它消掉了"必须有数据才能用"这个前提。**
一个需要数据才能启动的组件，在冷启动时是**不可用的**（鸡生蛋）。LLM 是唯一能
**零数据启动、且长期可被自己的产物替换**的组件 —— 这个"**可被自己淘汰**"的性质，
才是它能被安全放在关键路径上的理由：**它不会退化成永久依赖。**

**三阶段跃迁（同一个接口，替换零成本）：**

| 阶段 | 疑点消解器 | 需要的数据 | 特征来源 |
|---|---|---|---|
| **冷启动** | LLM（零样本，世界知识当先验） | 0 | 世界知识 + 渲染的目录 |
| **积累期** | LLM + 案例缓存命中（§6.6） | 少量 `(x, y)` | 上面这些 + 相似疑点的历史答案 |
| **成熟期** | 拟合的小分类器 / 规则表 | 足量 `(x, y)` | **纯符号特征** |

**关键：因为疑点被结构化成 `(kind, 候选符号特征, 上下文) → 索引`，
第三阶段要学的是一个"表格分类器"，不是一个"NLP 分类器"。**

| | 疑点若为原始自然语言 | 疑点被结构化（本方案） |
|---|---|---|
| 要学的东西 | NLP 分类器（需要嵌入 / 特征工程） | 表格分类器（离散、低维、可解释） |
| 样本需求 | 大 | **低一到两个数量级** |
| 可解释性 | 差 | 好（每个特征都是符号量） |

**所以"结构化"不只为了让 LLM 好回答，更是为了让 LLM 自己被淘汰。**
—— 这句话同时解释了 §6.3 为什么是硬性前提，而不是风格偏好。

**一条诚实的反面**：LLM 的世界知识是**启动成本，也是偏差来源**。
若私有域里术语的含义与常识不同（"train" 在某个业务里指"训练"而非"火车"），
LLM 的强先验会**主动误导**，而传统分类机没有这个风险（它只学你的数据）。
这构成"第三阶段"的第二个动机：**不只是省调用，更是摆脱先验偏差。**

### 6.9 让 LLM 直接出整张图，再让算法提取——可以，判据只有一条

**先分清楚两件事**（这是最容易混的地方）：

- 说"LLM 不擅长生成 DAG"，指的是**把它当学习任务**：训一个 `task → DAG` 的结构化预测器。
  样本需求高，Beyond ReAct 里 GPT-4o 的 DAG Exact Match 只有 **0.098**。
- **推理期**让现成 LLM 出草图、算法再提取校验，是**另一件事，而且合理**。
  文献里就是 **LLM-Modulo**（LLM 是 candidate generator，符号层是 verifier）与
  **TAMP**（最贴切），二者都表明"LLM 出草图 + 符号层校验补全"强于"LLM 端到端出计划"。

**判据只有一条，不是程度问题：**

> **这张图的正确性，算法在拿到它之后能不能判掉？**
> 能判掉 → 放手让 LLM 出整图（一次调用换一张图，最划算）。
> 判不掉 → 退回只让它做"选哪条边"（假设空间 = 候选池大小）。

⇒ **LLM 可以是图的候选来源，不能是图的权威。**
要避开的是 **LLM+P** 那种粗档（译成 PDDL 整体交给规划器、失败整体回退重来）——
它的病不在"用了 LLM 出图"，在**没把错误定位到具体某处**。

**"算法提取"= 四道关，每道关都必须响亮失败：**

| 关 | 做什么 | 失败时 |
|---|---|---|
| parse | 文本 → 结构（JSON / DSL） | 格式错 / 截断 / 多余字段 → **拒绝，不猜** |
| resolve | 名字 → `cat_id` / `iface_id`（`agent_cat_id`） | 目录外引用 → 报"闭包外引用" |
| close | 补 LLM 没写的中间边（TTN 可达性） | 不可达 → 无解，不"凑一条" |
| verify | 复用注册期不变式那套 | 有环 / 端口不齐 / 越天花板 / 超预算 → 拒绝 |

**第三条最要紧也最容易做丢**：LLM 给的图**不是 DAG 本身，是 DAG 的一个约束集**；
真图由算法在类型图上补全。**把它当查询，而不是当答案**，出图就没有正确性负担。

> 一旦提取器开始"宽容"（容错补全格式错误），它就在**悄悄替 LLM 承担正确性**。
> 拒绝而不是猜 —— 猜错 = **静默错连**，热插拔世界里最贵的那类 bug。

**更优形状：要"约束 + 显式缺口"，不要完整图。** 把 §6.3 反过来用——**LLM 也能提出疑点**。
差别是**构造式 vs 声明式**：构造式（"这是图"）要算法全量验证，O(图)，错了逐边回查；
声明式（"我要这两件事，谁接谁我不确定"）只需逐项查证，近乎 O(1)，缺口由 TTN 补，
而且**天然可结构化**——直接落进 §6.3 那张表，也就直接落进 §6.8 的第三阶段路径。

**统一视图（这条最重要）**：**LLM 只是多一路召回器，不是特殊路径。**
BM25 召回目标类型 / TTN 可达性召回候选图 / LLM 草图召回一种连接方式 ——
**多路召回 + 同一套校验器 + 排序**，与检索系统的形状完全一样。
§7 第 2 步让 `plan_search` 返回"候选集合 + 疑点列表"，正是为了把三路召回
**倒在同一个盘子里**，而不是给 LLM 开一条旁路。

### 6.10 "让 LLM 出约束、算法拿约束出图"——两处必须钉死的口径

**第一处：不是"改成不出图"，是"图由谁出"。** 出整图与给约束**两条都允许**，
选哪条由那条判据决定；义务不在"LLM 别画图"，在**"图不能是 LLM 的权威"**。

**第二处（更关键）：约束之后"出图"那一步必须是算法，不能又是 LLM。**
若是"LLM 出约束 → 再让 LLM 拿约束出图"，那只是**一次调用变两次**、自由度挪了个位置，
**没换来任何可验证性**。正确形状是**只有一次 LLM 调用**：

```
LLM 出约束集 ──> 算法 TTN 构造（枚举可达路径并过滤）──> 校验 ──> 确定性图
```

**图的构造权属于算法；LLM 只提供"对解的谓词"。**

**"LLM 擅长写约束文档"这句对，但陷阱在"文档"两个字上。**

> **约束的合格判据不是"写得好不好"，是"每一条能不能被机械判定真假"。**
> 可判定 ⇒ 好（算法拿它当真值）。散文式（"价格要便宜"）⇒ 坏，因为需要**另一个 LLM
> 或人来理解**，等于换个地方藏自由度，退化回最坏情况。

⇒ 谓词必须取自我们提供的词表/字段表（`cat_id` / `iface_id` / `trust` / `cost` / `type`），
**假设空间因此可枚举** —— 这决定了它的成本与可靠性。

**为什么约束比整图可靠：本质差别是"错误会不会级联"。**

| | 出整图（构造式） | 出约束（声明式） |
|---|---|---|
| 假设空间 | 所有合法图（指数级） | 所有可判定谓词（**可枚举**） |
| 输出长度 | O(节点数 + 边数) | O(约束条数) |
| 一处错 | **结构性错误，级联**到下游边 | **只砍掉一批解**，不级联 |
| 算法能说 | "图不对" | **"是第 3 条把解砍没了"** |

三条现成红利，都是本项目味的：

1. **不可满足性可定位**：无解时逐条摘约束重跑可满足性，就得到"**是这条导致无解**"——
   既是错误定位，也是**约束的重要性排序**（可解释）。对照 LLM+P 只能整体回退重来。
2. **确定性**：约束 + 算法 = 确定的图 ⇒ **不确定性锁在"产约束"这一小段**，之后每步可复现，
   直接对上确定性宪法。整图做不到（温度/版本一变图就变）。
3. **可缓存且粒度对**：同一 task 家族 = 同一份约束，命中即不调 LLM（接 §7.1 世代缓存）；
   "一张具体图"的缓存粒度太细，几乎不命中。

**约束的三种形态，都过同一套校验器**（表达力够，且不引入新的正确性来源）：
- **谓词 / 必须满足**：如"结果按 price 升序取第一个"
- **锚点 / 必须出现**：如"必须含 `travel.train`"（半构造式，补救谓词表达不了的形状）
- **禁止 / 不能使用**：如"不得使用 `trust > IO` 的能力"

**诚实的代价**：谓词表达力有限，**时序形状**不好表达（"先 A、再 B、再 A"）。
所以别把约束当万能——这正是要保留"锚点"的原因，也需要无解时**把失败反馈给 LLM 改约束**
（只改那一条，不是整体重来）。

**再进一步：LLM 出了定义之后，带着定义再让 LLM 出路径 —— 这是第几档？**

比"自由出图"精细一档，方向对。但"第几档"要先分开**两个轴** —— 混进一张表必出歧义：
一个轴讲"给 LLM 的**东西**有多大假设空间"，另一个轴讲"`plan_search` 跑**哪种策略**"。

**轴一：「形态」—— 给 LLM 的是什么。按假设空间递减。**

| 形态 | 给 LLM 的是什么 | 假设空间 | 谁保证正确性 | 评价 |
|---|---|---|---|---|
| `F1` | 任务描述，自由生成路径 | 所有合法图（指数级） | LLM（不可靠） | ✗ **不可表达** |
| `F2` | **约束集**，在约束下生成路径 | 满足约束的图（仍可能很大） | 仍要过 verify —— **约束对 LLM 只是提示** | △ |
| `F3` | **已枚举的候选集合**，从中选择 | k（候选数） | **算法**（枚举时已保证） | ✅ |

**本质的那一句：同一份约束，对 LLM 是提示，对算法是保证。**
所以**约束必须由算法执行**；LLM 的可靠位置是形态 `F3`——在已枚举候选上做选择，
那才是分类，才是它可靠的档。"已有的条件下生成"只要把"条件"明确成
"**已经枚举好的候选集合**"（而不只是"约束"），就正好落到 `F3`。

**轴二：「档位」—— `plan_search` 的策略枚举。按 LLM 参与度递增。**

| 档 | 名 | 做什么 | 对应形态 | 假设空间 | 评价 |
|---|---|---|---|---|---|
| 0 | `RULE` | 纯算法：类型图上可达性枚举 → 唯一解 | —（零 LLM） | 1 | ✅✅ **默认** |
| 1 | `TEMPLATE` | 命中 HTN 方法库 / CBR 案例库（§7 第 5 步） | —（零 LLM） | 1 | ✅✅ **默认** |
| 2 | `SELECT` | 算法枚举候选 → **LLM 只答索引** | `F3` | k | ✅ |
| 3 | `GENERATE` | 约束不完整时让 LLM **补约束**（回到档 2） | `F2` | 大 | △ **非默认** |

**不变式：档位的值域里，没有任何一档映射到 `F1`。**
「让 LLM 自由生成整图」在这个设计里**不是"不推荐"，是"不可表达"** ——
它没有档位、不能作为入参、传不进来。

> 这是把"禁令"写成**结构**而不是写成一句劝告：与其约定"别这么干"，
> 不如让那个状态在枚举里根本不存在。不变式的目的从来不是禁止状态，
> 是禁止**没人知道**的状态 —— 而"没有档位"比"有档位但约定不用"少一整类漏洞。

**档位是 `plan_search` 的显式入参，不是内部启发式。**

「默认」的定义不是"最常被选中"，而是**没有额外信息时系统自己会走的那一步**。
所以默认只允许取档 0 `RULE` 或档 1 `TEMPLATE` —— 这两档**不调 LLM**；
两库为空时档 1 自然退化成档 0，不需要特判。

档 2 是 LLM 唯一的**可达**位置，触发条件是**档 0/1 给不出唯一解**；
且它**调了也只答一个索引**。
档 3 需要更严的升级条件（约束不完整），且**跑完必须回到档 2** —— 它不产出图。
（第一版两库皆空 + `τ` 恒等于"无疑点"，所以实际只会走档 0。）

这么做把"LLM 调用量"从散落各处的隐式行为，变成**一条可观测曲线**：
档 0/1 的覆盖率上升 = 算法在自我增强（接 §6.6 飞轮）。**档位对外可见、可配、可断言。**

> ⚠ **跨文档引用一律带档名**（`RULE` / `TEMPLATE` / `SELECT` / `GENERATE`），**不带裸数字** ——
> 编排蓝图类文档也各有一套命名策略（如 `RULE_BASED` / `TEMPLATE` / `HYBRID` / `LLM_DRIVEN`），
> 名字相近但语义不等价，裸数字必然对错。

**因此链条差的那一环是"算法枚举"，且它是承重的：**

```
① LLM 出约束 ──> ② 算法在类型图上枚举候选（多项式，保证满足约束）
                        ──> ③ 有多个合法解时，才问 LLM「选哪个」（分类，答索引）
                        ──> 无解时，回给 LLM 改约束（只改那一条）
```

**禁令：候选集合一旦由算法枚举出来，就不许再让 LLM 重新生成整张图。**

这是档 2 `SELECT` 最常见的**伪装形态**：把候选拼进 prompt，然后要求 LLM"据此输出完整的 DAG"。
它看起来像档 2（候选确实参与了），实际退回形态 `F1` —— **枚举出的候选只是提示，不是保证**，
而且**没有任何一处能校验"LLM 的图 ⊆ 候选集"**。

> 轴二的不变式已经在**档位层面**让它不可表达，但**绕过档位直接调 LLM 的代码路径**仍可能存在
> —— 所以这条禁令不能只靠枚举，它同时是**调用点**上的约束。

> **真实反例**（2026-08 的一份编排蓝图实现）：`diverge()` 枚举出候选列表 → 该列表
> **只被拼成 prompt 文本** → `converge()` 返回的 `nodes/edges` **直接构造 DAG，零处比对**。
> 全库该候选类型的消费方**只有那一处 prompt 拼接** —— 候选集从未作为约束存在过。
> ⇒ **候选枚举这一步白做。**

**正确形状**：算法持候选（每条有 id），LLM 的输出**只有一个索引** —— `{"chosen": 2}`。
一句判据：**"LLM 的输出里能不能出现候选集中不存在的 id？" —— 能，就还是形态 `F1`。**

⇒ **"带着定义再出路径"不是默认动作，是有条件的**：
约束已唯一确定路径 → 算法直接算完，**不必第二次调用**；
仍有多个合法解 → 才需要第二次调用，且它回答的应是**索引**；
无解 → 更不该出路径，该改约束。

**但有一类情形确实非它不可**：**约束不完整**（自然语言需求没能完全形式化，
autoformalization 是公认瓶颈）。此时算法枚举出来的可能是空集或一堆无关的——
缺的约束算法不知道。此时"让 LLM 出路径"**有价值，但价值不在路径本身，
而在路径隐含地暴露了它补上的那些约束**。⇒ 要求它**把补的约束说出来**，回到 ①。
**这条链是迭代的，不是线性的。**

**一个务实的变体：一次调用同时要两样。** 让它一次输出"约束集 + 它选的那条路径"，
然后**检查它选的路径是否满足它自己写的约束**——不满足 = **约束写漏了**。
这是**免费的自洽性诊断**（分开两次调用则得不到这个交叉验证）。

### 6.11 让 LLM 输出数学语言去做定义/规划 —— 相关研究，以及我们该停在哪一层

**先分清两件事，"定义"和"规划"不是一个难度档：**

- **定义（声明式）**：LLM 给变量 / 约束 / 目标，不给出解。**可行，且是当前主流。**
- **规划（构造式）**：LLM 直接给出解的骨架（如整份 PDDL 的 plan）。**我们该避开** ——
  见 §6.9 关于 LLM+P 整体回退的批评。

⇒ 你措辞里的"**定义**"比"规划"精确得多：**让 LLM 承担"定义"，别让它承担"规划"。**

**相关研究谱系（按"输出的形式系统"分，不是按论文年份分）：**

| 形式系统 | 代表工作 | 关键机制 | 对我们的取舍 |
|---|---|---|---|
| PDDL（经典规划） | LLM+P、LLM-DP、Guan et al.(NeurIPS'23) world-model 修正 | LLM 译 → 规划器解 → 失败反馈回 LLM | **整体回退，避开**。Guan 那篇把"人修 PDDL"做成闭环，比 LLM+P 好，但仍把规划交给 NP-hard 求解器 |
| **一阶逻辑 / SMT** | **SATLM**(NeurIPS'23)、**Logic-LM**(EMNLP'23)、**LINC**(EMNLP'23) | LLM 做 semantic parser 输出 FOL → prover 推理 | ✅ **最贴合**。可判定 + 求解器能给 **unsat core** |
| 一阶逻辑 / ASP | LLM+ASP(Ishay et al.'23) | LLM 生成 Answer Set Program → clingo | 可用，非单调逻辑比 FOL 更强，代价是求解更贵 |
| 线性/整数算术（LP/MILP） | **OptiMUS**(ICML'24)、**LLMOPT**、NL4Opt 竞赛 | LLM 建优化模型（变量/约束/目标）→ 求解器 | 只在真要做"成本/偏好加权"时才上；**建模错求解器查不出来** |
| 时序逻辑（LTL/STL） | **AutoTAMP**(ICRA'24) | LLM 当 **translator + checker**，形式化规范做 verified | 用不到（我们没有连续时间约束） |
| 依赖类型（Lean/Coq） | **Draft-Sketch-Prove**(ICLR'23)、AlphaProof | 骨架 + **hammer 自动填空** | 表达力过剩，自动补全**不可判定** |
| 程序（可执行的数学） | **FunSearch**(Nature'24)、OPRO | LLM 生成程序，**evaluator** 打分做进化搜索 | 思想可取（evaluator 是承重墙），形态不适用 |
| 几何辅助构造 | **AlphaGeometry**(Nature'24) | LLM 只提"加哪条辅助线"，其余全交给符号引擎演绎 | ✅ **最值得抄的形状**（见下） |

**关键判断一：表达力越强，自动判定越难。所以不是越强越好。**

| 层 | 可判定性 | 能否定位错误 |
|---|---|---|
| 命题 / **有限域一阶** | **完全可判定** | ✅ **unsat core（现成）** |
| 线性 / 整数算术 | 可判定（有求解器） | 部分（建模错 vs 推理错难分） |
| 时序逻辑 | 可判定（模型检查） | 可（反例轨迹） |
| 依赖类型 | **不可判定**（自动补全） | 靠交互式证明 |

⇒ **我们停在第 1 层（命题 / 有限域一阶）就够，不要往上爬。** 理由很具体：
有限域上的约束可编码成 SAT/SMT，于是**"哪几条约束互相矛盾"由求解器直接给出
（unsat core）** —— §6.10 说的"无解时定位到具体哪条约束"，这里是**现成实现**，
不用自己写逐条摘除搜索。

**关键判断二：数学语言只用在"约束"这一层，不用在"结构"这一层。**

我们的问题形态是"从目标类型沿产出者倒推能力图"，**它本身是多项式可达性**（BFS）。
若把整张图编码成 CSP/SAT 一次求解，就把**多项式问题升格成 NP-hard**。
所以默认是**两段式**：

```
TTN 可达性（多项式，枚举候选）──> 约束过滤（SAT/SMT，可判定 + unsat core 定位）
```

只有当约束确实构成组合难题时，才考虑把"选哪些边"整体编码成一次 SAT 求解
（每个 `cat_id` 一个布尔变量，端口匹配当约束）。**默认不做。**

**关键判断三：`unsat core` 是白捡的，必须用。**
SAT/SMT 求解器（Z3 / MiniSat 系）标准输出不可满足核心。**这正是我们需要的错误定位**，
而且它是**约束的重要性排序**的副产品 —— 可解释性不用自己造。

**关键判断四：约束的谓词只能取自我们**已有**的词表，不要引入第二套形式系统。**
`cat_id` / `iface_id` / `trust` / `cost` / `type` 就是我们的符号量。
一套词表多处消费（§7.1 渲染给人看 / §1.4 检索当强判别词 / 这里当谓词的取值域）——
两套词汇表意味着两套一致性维护，不划算。

**关键判断五（最实用的一条）：约束的"语法"可以在解码层强制，不必事后 parse。**
**Grammar-constrained decoding**：llama.cpp 的 GBNF、Outlines、XGrammar、SGLang 的
压缩 FSM —— 让模型**在解码时只能生成合法 token**。
- 红利：§6.9 的 parse 关从"事后拒绝"变成"**根本生成不出来**"；输出长度可控。
- 做法：constraint grammar 由我们从目录**自动生成**（和 §7.1 的渲染同源 —— 同一份词表，
  一次渲染给人、一次渲染成 grammar 给模型）。
- **反面证据必须接受**：Tam et al. (EMNLP'24 Industry) "Let Me Speak Freely?" 显示
  **格式限制会损伤推理任务的表现**（尤其 JSON mode）。
  ⇒ 设计上要**把"自由思考"与"结构化输出"分开**：让它先把推理写出来（不加约束），
  最后一步再约束解码成约束集；或者干脆自由文本 + 事后严格 parse（见 §6.9 的红线）。

**关键判断六：翻译是瓶颈，推理不是。**
Autoformalization 的准确率从 Wu et al. (NeurIPS'22) 起就是瓶颈，至今没有解决。
求解器保证的是"**给定形式化模型之后的推理正确**"，**不保证"形式化模型忠实于意图"**。
再加一条同类的坑：**建模错误求解器查不出来**（OptiMUS / LLMOPT 都要 self-debug 正是此因）。
⇒ 结论：**verify 只能验形式合法性，必须另配"锚定测试"** ——
拿几个已知答案的样例去跑这份约束集，对齐预期。**约束集也要有测试。**

**关键判断七：AlphaGeometry 是最值得抄的形状，不是它的数学。**
LLM 只在符号引擎卡住时提供**有限跳跃**（加一条辅助构造），其余全部交给演绎。
**这就是 §6 的"疑点"的数学语言版本。** 两者不冲突：

> **数学语言处理"能精确的部分"，疑点机制处理"无法精确的部分"。**

**必须接受的负面结论（Valmeekam 一派）：**
- **PlanBench**（NeurIPS'23）：LLM 的规划能力在基准上很差，别高估。
- **"Can LLMs Really Improve by Self-critiquing Their Own Plans?"**（2023）：
  **self-critique 不可靠** ⇒ verifier 必须是**外部符号层**，不能让 LLM 自查。
  这正是 §6.9 那四道关存在的依据 —— 它不是洁癖，是有实证支撑的。

## 7. 落地顺序建议（对齐 §10.6 第 1 项）

按"每一步都能独立断言"排序，前两步不依赖任何外部条件：

1. **受控类型词表** —— ✅ **已落地**（`docs/agent.md` §10.6）。
   落法比这里的初稿更明确：接口类型是**第三个稠密 id 空间**（`iface_id`），
   不复用框架的布局类型 `cxf_type`（理由见 `agent_caps.h`：粒度不同 / 语义角色不同 /
   **生命周期冲突**——"类型永不卸载"与"能力必须热插拔"若同一物，插件带来的新类型永远
   卸不掉）。`CapDef` 加 `in_iface[CAP_IN_MAX]` + `out_iface`，`*_schema` 降格为渲染用注解。
   不变式 6/7/8 已进 `catalog_rebuild`：端口引用的类型名必须已注册；`INT` 必须至少被一个
   能力产出（悬空入口）；`EXT` 必须至少被一个能力消费且能力不得产出 `EXT`（死的入口）。
   等价是 **nominal 而非 structural** —— 三个接口类型刻意结构同形（都是 `<tag>|<price>`），
   语义差异正是 nominal 该管的。
2. **TTN + 反向邻接** —— 邻接表已随第 1 步落地（`cat_out` / `cat_in` / `prod_head+next`
   / `cons_head+next`，**建在 cat 空间、节点按端口编址**，见 `docs/agent.md` §10.6）。
   **待做**：`plan_search(goal_type)` 的 BFS（零分配，用 arena 帧栈 push/pop）。
   **关键：它返回候选集合 + 疑点列表，不返回"最优解"** —— 选择不是它的职责（§6.1）。
   **疑点由纯算法判定**（§6.7）：只用符号特征打分，`margin = score(top1) − score(top2) ≤ τ`
   才标疑点 —— 于是 `τ` 是**唯一需要调的参数**，且它把"模型调用量"变成一条连续曲线。
   断言：产物叶子数、所有 cat_id 都在目录视图内、**DAG 无环**、分解期零查找
   （`find_count` 不增长）、**候选数不超过预算**、
   **每个叶子都被一个能力整体承接**（类型侧可判，复用 `chain_reachable`）——
   接不住的不许静默通过，进疑点（§2.5），因为它不是"参数写错了"，是**它还是个复合任务**。
   注意这两种错的后续完全不同：参数错 ⇒ 改参数；叶子不是真原子 ⇒ **改分解**。
   第一版 `τ` 可以先恒等于"无疑点"。
3. **倒排索引 + BM25**：索引 `name`（切分后）+ `desc` + `in_type/out_type` 的**字段名**。
   查询期零分配。断言：**同一 task 两次打分逐字节相同**（确定性）、得分可逐项打印。
4. **接线 + 疑点出口**：BM25 选**目标类型** → TTN 搜候选 → 摘出 `Ambiguity[]`（§6.3）→
   交疑点消解。此时 HTN 方法库与 CBR 案例库**都是空的**，系统仍然能跑；
   而疑点消解第一版可以是**人**（打印疑点让人选）—— 先把接口和断言跑通，模型随时可插。
   **LLM 侧的接口按 §6.10 设计**：它的产出是**约束集（谓词 / 锚点 / 禁止）**，
   **不是图**；图仍由 `plan_search` 构造。这样"模型随时可插"才是真的可插——
   换成人、换成规则表、换成拟合出的小分类器，接的都是同一个 `(约束, 缺口)` 结构。
5. **可选加料**：HTN 方法库（把现有 `AGENT_PLAN_*` 数组升级成数据）、CBR 案例库（复用 §7.1 世代缓存）、
   疑点答案的结晶（§6.6）、**约束集的缓存**（同 task 家族命中即不调 LLM，§6.10）。
6. **形式化（只在需要时，§6.11）**：默认**两段式** —— TTN 可达性枚举候选（多项式），
   约束过滤交给 SAT/SMT（可判定），**无解时白嫖 `unsat core` 定位到哪条约束**。
   **不要把整张图编码成一次 SAT 求解**（那会把多项式问题升格成 NP-hard），除非约束确实
   构成组合难题。谓词取值域**只用已有词表**（`cat_id` / `iface_id` / `trust` / `cost` / `type`），
   不引入第二套形式系统。
   **配套两件事**：(a) constraint grammar 由目录**自动生成**（与 §7.1 渲染同源，
   同一份词表渲染两次：一次给人看、一次给解码器用），把 §6.9 的 parse 关从
   "事后拒绝"变成"生成不出来"——但注意 Tam et al.'24：格式约束会损伤推理，
   所以**自由思考与约束输出要分两段**；(b) **约束集也要有测试** ——
   拿几个已知答案的样例跑一遍对齐预期，因为 verify 只能验形式合法性，
   **建模错误求解器查不出来**。
